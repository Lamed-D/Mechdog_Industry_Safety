# 본체 Python: main 적용 전 사용자 동작 점검

**통합 main을 본체에 적용하기 전에 아래 실물 동작 테스트가 필요합니다.**
코드·가짜 모듈 테스트는 통과했지만 실제 A/B는 아직 미실행입니다. 한 대씩 별도로 기록합니다.
카메라 펌웨어 완료만으로 본체 동작이 검증되지는 않습니다.

## 0. 준비와 근거

**본체 코드 백업은 사용자 보고로 이미 완료됐습니다.** 업로드 담당자는 기존 백업과 대상 보드의 대응 및 복구 위치를 확인합니다.

- [ ] 대상 A/B, 실행할 항목 하나, 시험 범위를 사용자가 정함. 에이전트는 장치에 접속·업로드·구동하지 않음.
- [ ] 기존 백업의 대상·복구 방법 확인. 자동 실행을 중단하고 기존 프로그램이 다시 실행되지 않음을 확인.
  편집기의 Download and Run은 재시작을 동반하므로 기존 main의 자동 동작에 주의. 시험 파일을 main.py로 바꾸지 않음.
- [ ] 첫 시험은 추가 적재물을 빼고 지지 상태에서 수행. 바닥 주행은 별도의 빈 시험 공간과 전원 차단 수단 확보 후.
  손으로 다리를 붙들지 않음. 실제 적재 후에는 별도로 다시 확인.
- [ ] 본체의 실제 라이브러리 소스가 있으면 이를 먼저 대조. 없거나 frozen 모듈이면 소스를 보았다고 기록하지 않음.
  PC에서 해당 원본 Python 소스는 아직 찾지 못했으며, 실제 구현 인자/반환/초기화 대조는 **미완료**.
  가짜 모듈·Arduino 라이브러리를 Python 구현 근거로 대체하지 않음.

확인된 제조사 Python 예제의 호출·인자와 공식 문서를 보조 근거로 사용했습니다.
사용자 이동값 ±20/회전 ±5와 시간 300ms는 공식 범위 안의 작은 **초기 시험값**이며 이동 거리·정지 시간을 보장하지 않습니다.
배터리 7000mV와 동작 완료 대기 3초도 실측 전 가정입니다.
[공식 Python 안내](https://docs.hiwonder.com/projects/MechDog/en/latest/docs/4.Python_Programming_Projects.html).
소스·참고 자료·개인정보·장치 고유번호·비밀번호는 결과나 GitHub에 붙이지 않습니다.

## 1. 읽기·루프 확인: 아직 움직이지 않음

기존 main 자동 실행 중지 후, 시험 파일만 본체 최상위에 사용자 다운로드합니다.

| 항목 | 파일 / 사용자 실행 | 정상 관측 | A | B |
| --- | --- | --- | --- | --- |
| 공식 API·배터리 | `mechdog_only.py`의 `main()` | 필요한 호출이 True, 양수 mV. 객체 생성·보행 없음 | 미실행 | 미실행 |
| 후보 API | `api_candidates.py` | 존재 여부만 기록. 후보 메서드는 호출하지 않음 | 미실행 | 미실행 |
| I2C·IMU | `robot_imu_check.py`의 `run()` | angles·형식·호출 시간. 단위/칩 판별은 별도 확인. UART를 열지 않음 | 미실행 | 미실행 |
| 4개 루프·양보 | 아래 `robot_loop_check.py` | counts=[50,50,50,50], done 모두 True, errors/registration_error 없음, REPL 응답 유지 | 미실행 | 미실행 |
| 카메라 I2C | 기존 `vision_probe.py` 절차 | 응답/오류 기록. 맞춤 영상 펌웨어는 인식 결과 없음이 정상 | 미실행 | 미실행 |

REPL에서 루프만 명시적으로 시작합니다. 모션 객체·UART·Wi-Fi는 만들지 않습니다.

```python
import robot_loop_check as loops
import time
state = loops.run(allow_background=True)
time.sleep_ms(1000)
print(state)
```

등록 오류·일부 횟수 증가 없음·REPL 멈춤이면 통합 main을 적용하지 않습니다.
registration_elapsed_ms도 기록합니다. 등록 호출이 각 500ms 루프 완료까지 기다린다면 동시 실행을 확인한 것이 아닙니다.
**현재 main은 startMain 4개 동시 등록을 사용하므로 이 항목이 확인되기 전 실물 적용을 보류합니다.**

## 2. 항목별 실제 동작: 사용자가 각각 승인하고 실행

`robot_motion_check.py`는 import/Download만으로 움직이지 않습니다. 아래 호출은 **실제 움직임을 일으킵니다**.
먼저 stop만 수행하고 합격 후 나머지를 한 항목씩 실행합니다. `MechDog()` 생성 자체도 관측 대상입니다.

```python
import robot_motion_check as checks
print(checks.run("stop", allow_motion=True))
# 위 결과·실물 상태를 확인한 뒤 별도 승인한 항목 하나만 실행:
# print(checks.run("forward", allow_motion=True))
```

| 순서·case | 실제 관측할 것 | 실패 시 | A | B |
| --- | --- | --- | --- | --- |
| 1 stop | 초기화 직후 예상치 못한 보행 없음, 정지 유지 | 전원 차단·기존 프로그램/초기화 동작 확인 | 미실행 | 미실행 |
| 2 forward | 전진 방향·쏠림·300ms 뒤 정지 지연 | 반대 방향/불안정/계속 이동이면 중단 | 미실행 | 미실행 |
| 3 backward | 후진 방향·뒤 공간·정지 지연 | 다른 항목으로 넘어가지 않음 | 미실행 | 미실행 |
| 4 left | 작은 전진+왼쪽 회전. 제자리 회전 시험이 아님 | 방향과 보폭/회전 의미 재확인 | 미실행 | 미실행 |
| 5 right | 작은 전진+오른쪽 회전·정지 | 같은 조건에서 A/B 각각 기록 | 미실행 | 미실행 |
| 6 action | nodding_motion 시작·완료 반환과 실제 종료가 일치 | 3초 대기 초과/반환 불일치면 실패 | 미실행 | 미실행 |

완료/예외/Ctrl+C 경로에서 stop_action과 move(0,0)을 각각 시도합니다. 낮거나 알 수 없는 배터리는 시작하지 않습니다.
`calls_completed`는 API 호출 완료일 뿐 실물 합격이 아닙니다. 정지 지연·방향·이상음·접촉 여부를 사람이 기록해야 합니다.
공식 호출이 막히거나 전원이 불안정하면 소프트웨어 시간 제한/정지 호출이 제때 실행되지 않을 수 있습니다.
이상 시 다른 테스트를 실행하지 말고 현장 전원을 차단하고 복구합니다.

## 3. 통합 main 적용 여부

- [ ] 모든 필수 항목을 A/B 각각 관측하고 실패/측정 불가 항목을 검토함. 미실행이면 통합 적용 보류.
- [ ] [결과 양식](results-template.md)에 case·소프트웨어 결과·실제 방향·정지 지연·오류 종류를 기록함.
- [ ] 이후에만 [본체 main 업로드·복구](../robot-upload.md) 절차로 진행. 먼저 boot 래치·TEL만 확인하고 RESET/MOVE는 보내지 않음.
- [ ] 별도 통합 안전 시험에서 ESTOP·600ms 단절·Wi-Fi 복구 후 래치·A/B 역할 변경 정지를 확인함.
  단독 동작 시험은 통합 통신두절 안전 시험을 대신하지 않음.
