# 지금 할 수 있는 본체·카메라 점검

보유 장비는 MechDog와 장착된 비전 모듈입니다. Pi·라이다 연결 단계는 아직 하지 않습니다.
각 로봇 A/B에 대해 별도로 결과를 남깁니다. 하나만 확인했으면 다른 하나는 미확인으로 유지합니다.

## 사전 준비

1. 본체 전원과 배터리 상태, 다리·카메라 고정·케이블을 눈으로 확인합니다.
2. 제조사 Python Editor에서 **메인 보드**의 포트를 확인합니다. 비전 모듈의 Type-C 포트와 혼동하지 않습니다.
3. 기존 장치 main.py를 로컬 비공개 위치에 백업하고 복구 방법을 확보합니다. 기존 자동 동작을 중지한 상태에서 REPL에 접근합니다.
4. 아래 읽기 점검을 실행할 대상 A/B와 파일을 승인합니다. 새 펌웨어나 main.py는 업로드하지 않습니다.

## 본체 API 읽기

`tools/bringup/mechdog_only.py` 내용을 REPL에서 실행합니다. 파일 끝의 `main()`이 실행됐는지 확인합니다.
성공 기준은 필요한 API 항목이 true이고 배터리가 양의 mV 정수인 것입니다.
이 점검은 MechDog 객체를 만들거나 모션 API를 호출하지 않으며 UART·네트워크도 열지 않습니다.
실제 메서드 동작 검증은 아닙니다. 배터리 NA나 API false이면 다음 단계로 넘어가지 말고 결과를 보고합니다.

## 카메라 공식 Python 읽기

현재 실물 승인 범위는 **비전만**입니다. 위 본체 API·배터리 점검도 추가 승인 전에는 실행하지 않습니다.
COM6의 일반 REPL에서 `tools/bringup/vision_probe.py`를 단독 실행하면 다른 프로젝트 파일을 올릴 필요가 없습니다.
raw REPL이면 Ctrl+B로 나옵니다. Ctrl+D를 빈 일반 REPL에서 누르면 재부팅될 수 있으므로 누르지 않습니다.
현재 main.py에 모션 초기화가 있을 수 있어 Download and Run·Reset은 사용하지 않습니다.
정상 파일 첫 실행문은 함수 정의이며 `Hiwonder_IIC`와 `time`만 import합니다.
`IndentationError`는 카메라 통신 실패가 아니라 파일 손상/붙여넣기 오류입니다. 파일 내용과 들여쓰기를 먼저 복구합니다.
진단 출력은 VISION_ONLY_BEGIN, VISION_RESULT, VISION_ONLY_END입니다.
실패 시 stage와 errno로 버스 생성(iic_init)·카메라 생성(camera_init)·인식 읽기(face_read)를 구분합니다.
OSError만으로 카메라 고장이나 배선 오류를 확정하지 않습니다. 전원을 끈 상태에서 공식 IIC 케이블 연결을 확인합니다.
제조사 안내에 따르면 기본 카메라 펌웨어는 영상 전송을 지원하지만 인식 기능에는 해당 기능용 펌웨어가 필요할 수 있습니다.
현재 펌웨어 모드를 확인하기 전에는 카메라 펌웨어를 교체하지 않습니다. 영상 전송 성공과 face_recognition 성공은 별개입니다.
교체가 필요한 경우 [사용자 수동 펌웨어 가이드](../vision-firmware.md)에 따라 대상 카메라와 복구 파일부터 확인합니다.

카메라 펌웨어를 교체하지 않습니다. 제조사 예제 기준 연결은 `Hiwonder_IIC.IIC(2)`와
`Hiwonder_IIC.ESP32S3Cam`입니다. 기존 main.py를 보존한 채 **메인 보드**에 `robot/vision.py`만
`vision.py` 이름으로 준비하는 작업도 먼저 승인합니다. 이후 `tools/bringup/vision_official.py`를 REPL에서 실행합니다.

제조사 얼굴 강좌에서 물리 포트는 **IIC 1**, Python 버스는 **IIC(2)**입니다.
최신 단독 진단 버전 2는 `read_face()`가 있으면 우선 사용하고 선택 메서드를 출력합니다.
카메라 객체 생성만 성공하고 읽기가 실패한 경우에도 실제 연결을 정상으로 판정하지 않습니다.

- `status=observed`: 공식 호출이 결과를 반환했습니다. `has_result`의 변화와 유형만 기록합니다.
- `unknown`: 케이블·전원·버스·카메라 현재 기능 모드를 제조사 절차와 대조합니다. 임의 주소 스캔·raw I2C를 사용하지 않습니다.
- 결과가 없다고 카메라가 고장이라고 단정하지 않습니다. 기능 모드와 초기화 대기 시간은 실물 확인이 필요합니다.
- 얼굴 결과가 있더라도 쓰러진 사람을 검출했다는 뜻이 아닙니다. 실제 얼굴 영상은 첨부하지 않습니다.

출력이 멈추거나 예기치 않은 동작·발열·전원 반복이 생기면 즉시 중단합니다. 함수 호출 시간도 기록합니다.
공식 라이브러리의 I2C 읽기 시간 제한은 장치에서 확인해야 하므로 처음에는 수동 REPL에서만 시험합니다.

## 보고 양식

실물 확인 이슈에 A/B, API 지원 표, 배터리 mV 또는 NA, 카메라 status/result_type/has_result,
카메라 기능 모드, 호출 시간, 이상·미실행 항목을 적습니다. 개인정보·장치 식별번호·실제 영상·비밀번호는 제외합니다.
원본 영상의 HTTP 접근 주소는 기본 Python 결과 API와 별개이므로 확인 전에는 추측한 URL을 사용하지 않습니다.
