# 관리자 대시보드

시연 시나리오([demo-scenario.md](demo-scenario.md) 5절)의 관리자 화면입니다.

## 0. 기기 역할과 데이터 흐름 (사용자 결정, 2026-11-09 갱신)

### 0.1 기기 역할 (가정)

| 기기 | 역할 | 하는 일 |
| --- | --- | --- |
| **Raspberry Pi 5 16GB** (고정 위치) | **서버** — 로봇 지시·판단·주 DB | 로봇 A·B 명령·텔레메트리(UDP), 라이다 수신(TCP), 영상 수신·쓰러진 사람 감지, 시나리오 상태기계, **주 DB 저장**, 인터넷이 될 때 Supabase로 업로드 |
| **관리자 노트북** | **대시보드 실행** | Pi 5에 접속해 상태·알림을 보고, 사람 조작(전체 정지, 알림 확인, 안내 시작, 래치 해제, 조치 완료)을 Pi 5로 보냄. 판단과 기록은 하지 않음 |
| 로봇 A·B (MechDog) | 동작 | Pi 5의 명령을 공식 API로 실행, 명령이 끊기면 스스로 정지 |
| Supabase (인터넷) | **통합 관리용 사본** | Pi 5가 올린 기록을 기기별로 구분해 모아 둠. 외부 웹 관리·휴대폰 알림의 기반(후순위) |

- **모든 판단과 처리는 Pi 5에서** 합니다. 노트북 대시보드는 Pi 5의 화면·조작 창구일 뿐이고, 노트북이 꺼져도 로봇 제어·기록·안전 정지는 Pi 5와 로봇에서 계속됩니다.
- 노트북과 Pi 5는 시연 전용 공유기 안에서 연결합니다. Pi 5가 로봇들의 Wi-Fi 장치(접속점) 역할까지 맡을지는 실물 구성에서 정하며,
  그 경우 Pi 5의 인터넷 연결은 유선 랜이나 별도 USB Wi-Fi로 분리합니다(무선 칩 하나로 접속점과 인터넷을 동시에 하지 않음).
- 지금 코드(`dashboard/`)는 한 프로세스 안에서 핵심과 화면이 함께 도는 형태입니다. 이 구조로 가려면 **Pi 5 쪽 서버 API**(상태 조회·조작 받기)와
  **노트북 쪽 화면**으로 나누는 작업이 필요합니다(1단계 남은 일).

### 0.2 데이터 흐름

```text
 로봇 A·B ──UDP·TCP──▶ Pi 5 (서버)
                        ├ 시나리오 · 판단 · 로봇 지시
                        ├ 주 DB (Pi 5 로컬 SQLite) ← 모든 기록의 원본
                        ├ 상태·조작 API ◀──── 관리자 노트북 (대시보드 화면)
                        └ 업로드 대기열 ──(인터넷 연결될 때만)──▶ Supabase (통합 관리 사본)
                                                                 ├ (2단계, 후순위) 외부 웹 관리
                                                                 └ (3단계, 명세만) Android 휴대폰 알림
```

### 0.3 Pi 5 주 DB (1단계)

| 항목 | 내용 |
| --- | --- |
| 저장소 | Pi 5 로컬 SQLite 파일 하나(표준 라이브러리 `sqlite3`, WAL 모드). 저장소 밖 경로(예: `/var/lib/mechdog/main.db`) |
| 표 | `events`(지금 있는 사건 기록) / `alerts`(발생 시각, 로봇, 구역, 종류, 신뢰도, 상태 open→acked→resolved, 처리 기기·처리 시각, 증거 파일 로컬 경로) / `operator_actions`(어느 기기에서 어떤 조작을 했는지) / `robot_status`(1초 간격 요약) / `sync_outbox`(Supabase로 보낼 대기열) |
| 기기 구분 | 모든 행에 `hub_id`(어느 Pi 5인지)와, 해당되면 `robot_id`(A·B), `device_id`(조작한 노트북 등)를 넣습니다 |
| 원칙 | 기록 실패가 전체 정지·시나리오를 막지 않음(지금 `EventLog` 규칙 유지). 시각은 UTC 저장, 화면은 한국 시간 |
| 영상·사진 | DB에 바이트를 넣지 않음. 필요하면 Pi 5 로컬 경로만 기록하고 보관 기간을 정해 지움 |
| 백업 | 하루 한 번 DB 파일 백업(저장소 밖), 보관 기간·용량 상한을 설정값으로 |

`alerts`·`operator_actions`·`robot_status`·`sync_outbox`와 기기 구분 열은 아직 없습니다. 1단계 남은 일로 지금의 `EventLog`를 넓혀 만듭니다.

### 0.4 Supabase 업로드와 통합 관리 (2단계)

- **Pi 5가 인터넷에 연결될 때만** `sync_outbox`의 행을 Supabase로 올립니다. 인터넷이 없으면 쌓아 두었다가 연결되면 순서대로 보냅니다.
- 행마다 고유 ID(UUID)를 붙여 **같은 행을 두 번 올려도 한 번만 저장**되게 합니다(재시도 안전). 실패하면 간격을 늘려 다시 시도합니다.
- 업로드는 Pi 5에서 **밖으로 나가는 연결만** 씁니다(Pi 5로 들어오는 포트를 열지 않음). 영상·사진 바이트는 올리지 않습니다.
- Supabase에는 기기 표(`devices`: Pi 5 서버, 관리자 노트북, 로봇 A·B, 각 기기 종류·이름·마지막 접속 시각)를 두고, 모든 기록을 `hub_id`·`robot_id`·`device_id`로
  나눠 **기기별로 구분해 통합 관리**합니다. Pi 5가 여러 대로 늘어나도 같은 표에 모입니다.
- Supabase 키는 Pi 5의 `.env`에만 둡니다. 외부 웹 화면이 읽을 때는 읽기 전용 권한(행 단위 보안)을 씁니다.
- 업로드 지연·실패가 Pi 5의 시나리오·전체 정지·로컬 기록을 절대 막지 않습니다.

### 0.5 우선순위

| 단계 | 내용 | 우선순위 |
| --- | --- | --- |
| **1** | Pi 5 서버(로봇 지시·판단·주 DB) + 노트북 대시보드 | **높음 — 메인 시나리오에 필요** |
| 2 | Supabase 업로드·통합 관리, 외부 웹 관리 화면 | **낮음** — 메인 시나리오 완료 후. 웹은 중요도를 높게 잡지 않음 |
| 3 | Android 휴대폰 알림 | **낮음 — 명세만(5절), 개발은 메인 시나리오 완료 후** |

### 0.6 지금까지의 작업 단계

| 단계 | 폴더 | 내용 | 상태 |
| --- | --- | --- | --- |
| WP-D2 | `dashboard/core/` | 핵심 상태·사람 조작·사건 기록(웹 없이 테스트) | 완료(PC 테스트) |
| WP-D3 | `dashboard/web/` | 웹 서버·화면(가짜 로봇 모드). 실물 링크·영상 어댑터는 다음 단계 | 화면·서버 완료, 실물 연결 남음 |

## 1. 핵심 상태 (`dashboard/core`)

`DashboardCore(scenario, links, log)`가 시나리오 상태기계(`scenario/machine.py`), 로봇별 링크(`host/robot_link.RobotLink`),
사건 기록(`EventLog`, SQLite)을 묶습니다. 네트워크·웹 의존성이 없습니다.

| 조작 | 메서드 | 규칙 |
| --- | --- | --- |
| **전체 정지** | `estop_all()` | 확인 없이 바로. 모든 링크에 ESTOP을 걸고 즉시 한 번 보냄. 링크 하나·시나리오·기록이 실패해도 나머지는 계속하고, 실패 목록을 돌려줌(화면에 크게 표시) |
| 래치 해제 | `reset_latch(robot, confirmed=True)` | 확인 창을 거친 경우만. 신선한 래치 텔레메트리·배터리 조건은 링크가 검사. 실제 해제는 로봇 텔레메트리로 판단 |
| 알림 확인·안내 시작·재시도·조치 완료·순찰 시작·안내 재개 | `operator(event)` | 시나리오가 거부하면 `ok: False`와 이유 |
| 안내 멈춤 | `guide_blocked(reason)` | |

| 입력 | 메서드 | 처리 |
| --- | --- | --- |
| 링크 상태(10 Hz) | `update()` | 텔레메트리가 신선하고 래치가 풀리면 `robot_ready`. 끊기면 `link_lost`. **준비된 로봇이 스스로 래치되면**(저전압·감시 타이머 등) `robot_latched` 알림과 함께 준비 상태에서 뺌. 시나리오 시간 초과 처리 |
| 영상 감지 | `detection(result, zone)` | `host.vision.EvidenceMonitor` 결과. 알림 목록에 추가 |
| 도착 | `arrived(robot, target)` | 경로 실행 어댑터(D3)가 알림 |
| 카메라 수신 상태 | `camera_state(robot, state)` | `LatestFrameReceiver.state()`. 영상 없으면 `unknown` 표시 |

- 시나리오의 이동 명령(순찰·이동·안내·동작·자세)은 여기서 실행하지 않고 `drain_commands()`로 어댑터(D3)가 가져갑니다.
  `estop` 명령만은 어댑터를 기다리지 않고 바로 링크에 겁니다.
- `snapshot()`은 화면용 JSON(단계, 로봇 상태, 알림, 최근 알림 100개, 기록 실패 수)입니다.

## 2. 사건 기록 (`EventLog`)

- SQLite 한 표(`events`: 시각, 종류, 로봇, JSON 내용). 경로는 실행 시 지정, 기본은 메모리.
- 영상·사진 **바이트는 저장하지 않습니다**(`<bytes omitted>`로 바뀜). 필요하면 저장소 밖 로컬 경로 문자열만 남깁니다.
- 기록 실패는 예외 대신 실패 횟수로 알리며, 전체 정지 같은 조작을 막지 않습니다.
- 기록 파일은 현장 정보가 담기므로 저장소에 올리지 않습니다(`/logs/`, `outputs/`는 .gitignore).

## 3. 웹 서버와 화면 (`dashboard/web`)

표준 라이브러리만 씁니다(`http.server` + 200 ms JSON 폴링). 새 의존성이 없습니다.

```bash
python -m dashboard.web.run --sim                  # 가짜 로봇 A·B, http://127.0.0.1:8000
python -m dashboard.web.run --sim --host 0.0.0.0 --token <조작 토큰> --log D:\mechdog-logs\events.db
```

- `--sim` 또는 `--allow-real`을 명시해야 실행합니다. 실물 점검 어댑터는 한 소켓으로 두 로봇을 받고
  출처 주소·포트·로봇 ID를 대조합니다. 사용자가 대상 A/B를 승인한 뒤에만 아래 명령을 실행합니다.
  `python -m dashboard.web.run --allow-real --robot-a <A_IP> --robot-b <B_IP> --token <사용자 토큰>`
  실물 모드는 토큰이 필수입니다. HELLO/STOP/ESTOP과 사람이 확인한 RESET만 보냅니다.
  **순찰·경로·안내·동작·자세는 stationary_mode로 차단하고 정지합니다.** 경로 계획·실물 검증 전 이동하지 않습니다.
  시작·종료도 로봇으로 명령을 보내므로 에이전트는 이 명령을 실행하지 않습니다.
- 화면 맨 위 **전체 정지** 버튼은 확인 창 없이 바로 보내고, 실패하면 한 번 더 보낸 뒤 결과를 빨갛게 표시합니다.
- **전체 정지는 토큰 없이도** 받습니다(멈추는 쪽은 막지 않음). 순찰·안내 같은 조작과 래치 해제는 `--token`을 주면 토큰이 필요합니다.
- 래치 해제는 화면의 확인 창("주변이 안전하고 로봇을 지켜보고 있습니까?")을 거쳐야 하고, 서버도 `confirmed: true`만 받습니다.
- 서버와 연결이 끊기면 화면에 "정보가 오래됨"을 표시합니다. 로봇은 명령이 0.6초 끊기면 스스로 멈춥니다(규약 5.1절).
- 기본 주소는 127.0.0.1입니다. 관리자 노트북에서 열 때만 `--host`를 주고, 전용 공유기 안에서만 씁니다(HTTPS 아님).

## 4. 외부 배포 결정 (사용자, 2026-11-09) — 2단계, 후순위

> 0절 갱신에 따라 **기록 DB의 원본은 Pi 5 로컬 SQLite**이고, Supabase는 인터넷이 될 때 올리는 **통합 관리 사본**입니다.
> 대시보드는 관리자 노트북에서 실행합니다. 아래 표의 FastAPI 전환·cloudflared·Supabase 판은 메인 시나리오 완료 후 진행합니다.

| 항목 | 결정 | 할 일 |
| --- | --- | --- |
| 웹 서버 | **FastAPI + uvicorn** 사용 가능 | `dashboard/web/server.py`(현재 표준 라이브러리)를 FastAPI로 옮기고 화면 갱신은 WebSocket. 의존성은 `requirements-dashboard.txt`에 버전 고정·이유와 함께. `DashboardCore`·안전 규칙(전체 정지 토큰 없음, 래치 해제 확인)은 그대로 |
| 외부 접속 | **cloudflared**(Cloudflare Tunnel) | 대시보드는 계속 `127.0.0.1`에만 열고 cloudflared가 그 포트로만 연결. **Cloudflare Access(로그인) 필수**, 빠른 임시 터널(`--url`, 인증 없음)은 쓰지 않음. 카메라 스트림 포트·로봇 UDP·라이다 TCP는 터널에 넣지 않음 |
| 기록 DB | **Supabase**(Postgres) | `EventLog`와 같은 인터페이스(`record`/`recent`/`failures`)의 Supabase 판을 추가. **기록 실패·지연이 전체 정지를 막지 않게** 비동기 큐 + 로컬 SQLite 예비 기록 유지. 영상·사진 바이트는 올리지 않음 |

- Cloudflare 계정·터널 생성, Supabase 프로젝트·키 생성은 **사용자만** 합니다(비밀 정보). 키는 `.env`에만 두고 커밋하지 않습니다(`.env.example`에 이름만).
- 인터넷에 열리면 전체 정지 버튼도 인터넷에서 눌립니다. Access 로그인 뒤에만 열리게 하고, 로봇 쪽 정지(통신 끊김 0.6초)는 그대로 최종 안전 장치입니다.

## 5. Android 휴대폰 알림 — 3단계, 명세만 (개발은 메인 시나리오 완료 후)

쓰러진 사람 발견 같은 알림을 관리자 휴대폰(Android)으로 바로 보내는 서비스입니다. **지금은 명세만 두고 개발하지 않습니다.**

| 항목 | 명세 |
| --- | --- |
| 보내는 쪽 | Pi 5가 알림을 만들고, 인터넷이 될 때 푸시 서비스로 보냄. 후보: Firebase Cloud Messaging(FCM). Pi 5가 직접 보내거나 Supabase의 서버 함수를 거쳐 보냄(선택은 개발 시점에) |
| 받는 쪽 | 관리자용 Android 앱(최소 기능). 알림 표시 → 누르면 대시보드(외부 웹)나 알림 상세로 이동 → "확인" 누르면 Pi 5의 알림 상태가 acked로 바뀜 |
| 알림 내용 | 로봇 ID, 구역, 시각, 종류(쓰러진 사람·래치·배터리 등), 신뢰도, "확인 필요" 여부. **사진·얼굴·개인정보는 넣지 않음** |
| 종류·등급 | 긴급(쓰러진 사람, 로봇 래치) / 일반(배터리 낮음, 통신 끊김) / 정보. 같은 사건은 한 번만(중복 묶기) |
| 휴대폰 조작 범위 | 처음에는 **확인만**. 휴대폰에서 로봇을 움직이는 조작은 넣지 않음. 전체 정지를 넣을지는 인증·오작동 위험을 검토한 뒤 결정 |
| 실패 대비 | 인터넷이 없거나 푸시가 실패해도 현장 대시보드(노트북)와 로봇 쪽 안전 동작은 그대로. 실패는 Pi 5 주 DB에 기록 |
| 비밀 정보 | 푸시 서비스 키는 Pi 5(또는 서버 함수)의 비밀 설정에만. 휴대폰 등록 토큰은 Pi 5 주 DB와 Supabase `devices`에 저장, 저장소에 올리지 않음 |
| 계정·키 생성 | Firebase 프로젝트, 앱 서명 키, 스토어 배포는 **사용자만** 합니다 |
