# 관리자 대시보드

로컬 진단 서버의 `/api/estop`은 헤더 처리가 끝나면 본문 길이·JSON·도착을 기다리지 않고 먼저 전체 정지를 요청합니다.
일반 조작은 불완전한 본문·중복 길이/전송 방식 모호성을 거절하고 소켓 대기를 제한합니다.
이 동작은 Pi에 요청이 도착한 뒤의 처리이며, 인터넷 단절 시 원격 정지가 도달한다는 보장은 아닙니다.

로컬 래치 해제는 최신 상태의 `reset_context`를 확인 창이 뜨기 전에 잡아 함께 보냅니다.
서버는 로봇별·서버 실행별 공개 확인 ID를 발급하며 새 ESTOP·세션/정지 사유 변경·5초 만료·다른 로봇·재사용이면 거절합니다.
5초는 보수적 초기값이며 확인 창을 오래 열어 두었으면 새 상태에서 다시 확인합니다. 인증 토큰과는 별개입니다.
승인 뒤에도 해제 여부는 실제 TEL로 판단합니다. 이 변경을 쓰려면 화면과 서버를 함께 갱신합니다.

## 사건 정황 메타데이터

새 알림과 판단 갱신 때 `incident_context`를 기록합니다. 사건 ID·단계·신뢰도/임계/시간 창·근거 소스와,
당시 A/B의 링크·역할·래치·배터리·카메라 상태를 함께 묶습니다. 추론 작업자는 처리한 프레임의 순번·실제 차원·
취득 시각·SHA-256을 제공하며 원본 JPEG는 기록하지 않습니다. 다른 프레임의 정보가 섞이지 않도록 사본을 보존합니다.
이는 중앙 Pi에서 두 동일 장비의 상태를 사건 시각에 연결하기에 적합합니다. 영상은 메인 보드 I2C를 거치지 않으므로
프레임 메타데이터는 Pi의 HTTP 수신·추론 쪽에서 만들고 로봇은 짧은 TEL/ROLE만 보냅니다.

사용자 읽기 전용 내보내기: `python -m tools.export_incidents --db <Pi_SQLite_파일> --limit 100`.
기존 DB를 읽기 전용으로 열고 저장 완료된 사건을 UTC 시각·버전·evidence_source와 함께 JSON Lines로 출력합니다.
합성 사건은 source=synthetic으로 구분합니다. DB 수정·영상 파일 생성·업로드는 하지 않습니다.
사진 저장과 보관·접근 정책은 아직 구현하지 않았습니다. 화면 알림은 최근 100건으로 제한하고 원본 사건 기록은 DB에 남깁니다.

실물 고정 위치 실행 경로는 `BufferedEventLog(EventLog(...))`를 사용합니다. 제어 잠금 안에서는 메타데이터를
제한 큐에 넣기만 하고 SQLite 커밋은 별도 작업자가 처리합니다. 큐는 최대 512건, 건당 16KB이며,
가득 차거나 기록이 실패하면 log_failures를 올립니다. 기록 실패는 ESTOP 송신을 기다리게 하지 않습니다.
`record=True`는 큐 접수이며 디스크 저장 완료가 아닙니다. 기록 시각은 큐 접수 때 보존합니다.
정상 종료는 최대 1초 기다리고, 디스크가 막히거나 프로세스가 종료되면 미저장 메타데이터가 손실될 수 있습니다.
전체 정지·시나리오 잠금 안에서 기록 조회·flush·디스크 작업을 호출하지 않습니다.

실물 없이 전체 흐름을 연습하려면 `python -m tools.mock.demo_scenario`를 실행합니다.
`--finder B`로 두 ID의 동일 기능을 확인하고 `--fault link`, `--fault camera`, `--fault estop`으로 장애를 주입합니다.
가짜 시계·가짜 링크·메모리 SQLite만 사용하며 소켓·카메라·모델을 열지 않습니다. 출력 JSON Lines는 모두 synthetic입니다.
RESET·안내 시작·조치 완료는 **합성 사람 조작을 스크립트로 연습**하는 것이며 실물 자동 해제를 제공하지 않습니다.
전체 정지 주입은 estop에서 끝나고 재이동하지 않습니다. 이 데모는 경로·낙상 정확도·실제 통신 검증을 대신하지 않습니다.
사용자 실제 적용은 [통합 확인 순서](user-tests/integrated-bringup.md)를 따릅니다.

시연 시나리오([demo-scenario.md](demo-scenario.md) 5절)의 관리자 화면입니다.

## 0. 기기 역할과 데이터 흐름 (사용자 결정, 2026-11-09 갱신)

**대시보드는 무조건 인터넷으로, Supabase를 기준으로 동작합니다**(사용자 결정, 2026-11-09).
노트북 대시보드는 Pi 5에 직접 접속하지 않고, Supabase에서 데이터를 받고 Supabase에 명령·설정을 씁니다. Pi 5는 Supabase와 동기화하면서 로봇을 움직입니다.

### 0.1 기기 역할

| 기기 | 역할 | 하는 일 |
| --- | --- | --- |
| **Raspberry Pi 5 16GB** (고정 위치) | **로봇 서버** — 로봇 지시·판단, Supabase 동기화 | 로봇 A·B 명령·텔레메트리(UDP), 라이다 수신(TCP), 영상 수신·쓰러진 사람 감지, 시나리오 상태기계, 순찰 루틴 실행. 상태·알림·기록을 Supabase에 올리고, Supabase의 명령·설정(확정 지도·구역·루틴)을 가져와 검증 후 실행. 로봇망 핫스팟 + 인터넷 동시 연결(0.5절) |
| **관리자 노트북** | **대시보드 — 인터넷·Supabase 기준** | Supabase 실시간 구독으로 상태·알림·순찰 결과를 받아 표시·처리. 사람 조작(전체 정지, 래치 해제, 알림 확인, 안내 시작, 조치 완료, 순찰 켜기·끄기), 지도 검토·확정, 구역·지점·루틴 설정, 정찰 조종을 Supabase에 씀([mapping-and-patrol.md](mapping-and-patrol.md)). (3단계) Android 앱 알림 발송(5절). 인터넷만 있으면 어디서든 됨. 로봇 판단은 하지 않음 |
| 로봇 A·B (MechDog) | 동작 | Pi 5의 명령을 공식 API로 실행, 명령이 0.6초 끊기면 스스로 정지 |
| **Supabase** (인터넷) | **기준 DB** | 상태·알림·조작 기록·명령·지도·구역·루틴·기기 정보를 모으는 곳. 대시보드와 Pi 5가 함께 보는 기준 |

- **로봇 판단과 실행은 Pi 5에서** 합니다. 대시보드가 Supabase에 쓴 명령·설정도 Pi 5가 검증한 뒤에만 실행합니다.
- 노트북은 로봇망(Pi 5 핫스팟)에 붙지 않습니다. 노트북과 Pi 5 사이에 직접 연결이 없습니다.
- 지금 코드(`dashboard/`)는 한 프로세스 안에서 핵심과 화면이 함께 도는 형태입니다. 이 구조로 가려면 핵심(`DashboardCore`)은 **Pi 5 쪽 서비스 + Supabase 동기화**로,
  화면은 **Supabase를 읽고 쓰는 노트북 대시보드**로 나눠야 합니다(1단계 남은 일).

### 0.2 데이터 흐름

```text
 로봇 A·B ──UDP·TCP (로봇망, Pi 5 핫스팟)──▶ Pi 5 (로봇 서버)
                                              ├ 시나리오 · 판단 · 로봇 지시 · 순찰 루틴
                                              ├ 로컬 DB (실행용 사본 + 끊김 대비 대기열)
                                              └ 동기화 (Pi 5가 밖으로만 연결)
                                                    │ 올림: 상태·알림·기록       ▲ 가져옴: 명령·확정 지도·구역·루틴
                                                    ▼                          │
                                              Supabase (기준 DB, 지도 파일 저장소)
                                                    │ 실시간 구독               ▲ 명령·설정 쓰기
                                                    ▼                          │
                                              노트북 대시보드 (인터넷 어디서든) ──(3단계)──▶ Android 앱 알림(5절)
```

### 0.3 Supabase 기준 DB와 Pi 5 로컬 DB

| 위치 | 역할 | 내용 |
| --- | --- | --- |
| **Supabase**(Postgres + 비공개 파일 저장소) | **기준** | `devices`(Pi 5·노트북·로봇·휴대폰), `robot_status`(1초 간격 요약), `alerts`(open→acked→resolved), `events`, `operator_actions`, `commands`(0.6절), 지도·구역·루틴 표([mapping-and-patrol.md](mapping-and-patrol.md) 6절), `notifications`(5절). 지도 이미지는 비공개 파일 저장소 |
| **Pi 5 로컬 SQLite**(WAL, 저장소 밖 경로 예: `/var/lib/mechdog/main.db`) | 실행용 사본·대기열 | 가져온 확정 지도·구역·루틴의 사본(인터넷이 끊겨도 서버 위치로 복귀·정지할 수 있게, 0.7절), 올리기 전 기록을 쌓는 `sync_outbox`, 처리한 명령 ID(중복 방지) |

- 모든 행에 `hub_id`(어느 Pi 5인지)와, 해당되면 `robot_id`(A·B), `device_id`(조작한 노트북·휴대폰)를 넣어 **기기별로 구분해 통합 관리**합니다.
- Pi 5는 기록을 먼저 로컬에 쓰고 `sync_outbox`로 올립니다. 행마다 고유 ID(UUID)라 두 번 올려도 한 번만 저장됩니다. 끊기면 쌓았다가 연결되면 순서대로 보냅니다.
- 기록·업로드 실패가 전체 정지·시나리오를 막지 않습니다(지금 `EventLog` 규칙 유지). 시각은 UTC 저장, 화면은 한국 시간.
- **영상·사진 바이트는 Supabase에 올리지 않습니다.** 필요하면 Pi 5 로컬 경로만 기록하고 보관 기간을 정해 지웁니다. 실시간 영상은 대시보드에 처음에는 넣지 않습니다(넣을지는 개인정보 검토 후 결정).
- Supabase 프로젝트·키 생성은 **사용자만** 합니다. 키는 각 기기의 `.env`에만 두고 커밋하지 않습니다.

### 0.4 Supabase 권한 (행 단위 보안)

| 주체 | 할 수 있는 것 |
| --- | --- |
| Pi 5(기기 계정) | 자기 `hub_id`의 상태·알림·기록 쓰기, 자기 앞으로 온 명령 읽기·결과 쓰기, 확정 지도·구역·루틴 읽기 |
| 관리자(대시보드 로그인) | 상태·알림·기록 읽기, 명령 쓰기, 지도 확정·구역·루틴 쓰기 |
| 휴대폰 앱(3단계) | 자기 권한의 알림·상태 읽기, 알림 확인 쓰기 |

- Pi 5의 키는 Pi 5에만 두고, 대시보드·앱은 로그인한 사용자 권한으로만 접근합니다(모든 권한 키를 노트북·휴대폰에 두지 않음).

### 0.5 Pi 5 네트워크: Pi 5 핫스팟(로봇망) + 인터넷 동시 연결

**결정(사용자 요청 검토 결과):** Pi 5가 **직접 Wi-Fi 핫스팟을 켜서 로봇 제어용 메인 통신망**을 만들고, **동시에 다른 연결 장치로 인터넷**을 받습니다.
지금까지 문서의 "전용 공유기"는 이 Pi 5 핫스팟이 기본이 되고, 전용 공유기는 Pi 5 핫스팟에 문제가 있을 때의 **예비**입니다.
대시보드가 Supabase 기준이므로 **대시보드를 쓰려면 Pi 5의 인터넷이 꼭 있어야 합니다.**

| 연결 | 용도 | 구성 |
| --- | --- | --- |
| **로봇망** (안쪽, 메인 통신) | 로봇 A·B 메인 보드, 비전 모듈 2개 ↔ Pi 5. 명령·텔레메트리(UDP), 라이다(TCP), 영상 | **Pi 5 내장 Wi-Fi를 핫스팟(접속점)으로.** **2.4GHz**(ESP32·ESP32-S3는 2.4GHz만 지원), WPA2, 고정 채널(1·6·11 중 주변과 덜 겹치는 곳), Pi 5 주소 고정, 로봇·카메라는 고정 주소 또는 예약 주소 |
| **인터넷** (바깥쪽) | Supabase 동기화(상태·알림 올리기, 명령·설정 가져오기) | **두 번째 연결 장치**: ① 유선 랜(가장 안정) ② USB Wi-Fi 어댑터로 건물 Wi-Fi 접속(5GHz 가능하면 5GHz) ③ 휴대폰 USB 테더링(예비) |

검토 결과:

| 방식 | 판단 |
| --- | --- |
| **내장 Wi-Fi 핫스팟 + 유선 랜·USB Wi-Fi·USB 테더링으로 인터넷** | **채택.** 서로 다른 장치라 간섭이 없고, Ubuntu 24.04의 NetworkManager로 핫스팟과 인터넷 연결을 함께 설정할 수 있습니다 |
| 내장 Wi-Fi 하나로 핫스팟 + 인터넷 접속 동시에 | 비권장. 무선 칩 하나는 같은 채널에서만 두 역할을 할 수 있어, 인터넷 쪽 공유기가 채널을 바꾸면 로봇망이 끊깁니다. 로봇망이 2.4GHz여야 하므로 인터넷 쪽도 2.4GHz 같은 채널이어야 하는 제약도 생깁니다 |

용량 검토(추정, 실측 필요): 로봇망 접속 기기 4대(메인 보드 2, 비전 모듈 2), 영상 2개(각 약 1~2Mbps) + 라이다 2개(각 약 0.1Mbps) + 명령·텔레메트리(아주 작음).
내장 Wi-Fi 핫스팟으로 감당할 수 있는 범위로 보이지만, 두 대 동시 영상 시 지연·끊김은 실물에서 확인합니다 [실물 확인 필요].
인터넷 쪽은 영상을 올리지 않으므로 상태 요약·알림·명령 정도의 작은 양입니다.

- 로봇망과 인터넷 사이에 **라우팅을 하지 않습니다**(로봇·비전 모듈이 인터넷으로 직접 나가지 않음). Pi 5가 가운데서 필요한 데이터만 주고받습니다.
- Pi 5는 **밖으로 나가는 연결만** 씁니다. Pi 5로 들어오는 포트를 인터넷에 열지 않습니다(터널도 필요 없음).
- 핫스팟 이름·비밀번호, 인터넷 쪽 Wi-Fi 정보는 Pi 5 로컬 설정에만 둡니다(커밋 금지). 로봇 `secrets.py`, 카메라 `secrets.h`에는 이 핫스팟 정보를 넣습니다.
- Pi 5 핫스팟·인터넷 동시 설정 절차와 주소 계획은 `docs/host-setup.md`에 추가합니다(1단계 남은 일).

### 0.6 명령 경로: 대시보드 → Supabase → Pi 5

대시보드의 **모든 조작은 Supabase `commands` 표를 거쳐** Pi 5로 갑니다. 실행 여부는 항상 Pi 5가 정합니다.

```text
 노트북 대시보드 ──쓰기──▶ Supabase commands (pending)
                               │ Pi 5가 실시간 구독 + 1초 주기 확인(구독이 끊겨도 놓치지 않게)
                               ▼
                 Pi 5: 검증 → 실행(robot_link) → 결과(accepted/rejected/expired/done) 쓰기 → 대시보드에 표시
```

| 규칙 | 내용 |
| --- | --- |
| 검증 | 보낸 사용자 권한, 명령 종류 허용 목록, 대상 로봇, 유효 시간, 중복(명령 고유 ID) |
| 유효 시간 | 명령마다 만든·만료 시각. 늦게 도착한 명령(예: 10초 초과)은 실행하지 않고 "만료". **단 전체 정지는 늦게 와도 실행**(멈추는 쪽이 안전) |
| 전체 정지 | 가장 우선. 확인 창 없이 바로 씀. Pi 5는 받는 즉시 모든 로봇에 ESTOP, 루틴도 모두 정지 |
| 래치 해제 | 대시보드 확인 창("현장에서 로봇을 보고 있고 주변이 안전합니까?")을 거친 명령만. Pi 5가 신선한 텔레메트리·배터리 조건을 다시 확인하고, 실제 해제는 로봇 텔레메트리로 판단 |
| 시나리오·순찰 | 알림 확인, 안내 시작, 조치 완료, 순찰 루틴 켜기·끄기·지금 시작, 지도 확정·구역·루틴 반영 |
| 정찰 조종 | 지도 작성 모드에서만. 명령마다 유효 0.5초, 작은 보폭·회전 상한, 새 명령이 없으면 Pi 5가 정지. 인터넷 지연이 크면 자주 멈출 수 있음(안전한 쪽) [실물 확인 필요] |
| 기록 | 모든 명령의 누가·언제·무엇을·결과를 `operator_actions`에 남김(`device_id`로 노트북·휴대폰 구분) |

### 0.7 연결이 끊기면: 서버 위치로 복귀 후 정지 (사용자 결정, 2026-11-09)

**10초 이상 끊기거나 끊길 것 같으면, 로봇은 순찰을 멈추고 서버(Pi 5) 쪽 위치로 돌아갑니다. 그래도 연결이 돌아오지 않으면 서버 근처에서 정지합니다.**

| 경우 | 감지(Pi 5) | 동작 |
| --- | --- | --- |
| **인터넷 끊김** (Pi 5 ↔ Supabase) | Supabase 동기화가 **10초 이상** 실패 | 순찰 루틴 일시 정지 → 각 로봇을 **서버 위치**(확정 지도의 복귀 지점, [mapping-and-patrol.md](mapping-and-patrol.md) 4절)로 느린 걸음으로 이동 → 도착하면 `move(0, 0)` 후 앉기(`sit_dowm`)로 정지·대기 |
| **로봇망 약해짐** (로봇 ↔ Pi 5) | 텔레메트리가 늦거나 빠지는 비율이 기준을 넘음 = **끊길 것 같음**(기준값은 실측 후 설정. 신호 세기 보고는 로봇 쪽 추가 후보) | 그 로봇을 서버 위치 쪽으로 이동(핫스팟에 가까워지면 신호가 회복됨) → 회복되지 않으면 서버 근처에서 정지 |
| **로봇망 완전히 끊김** | 텔레메트리 없음 | 로봇이 0.6초 뒤 **그 자리에서** 스스로 정지(경로 계획이 Pi 5에 있어 로봇 혼자 돌아올 수 없음). 그래서 완전히 끊기기 전에 위 "약해짐" 단계에서 미리 돌려보냄 |

- 복귀 중에도 장애물 정지, 전체 정지, 래치, 금지 구역 규칙은 그대로입니다. 길이 막히거나 자기 위치를 잃으면 **그 자리에서 정지**합니다.
- **연결이 돌아와도 스스로 순찰을 다시 시작하지 않습니다.** 대시보드에서 사람이 상태를 확인하고 순찰 재개 명령을 보내야 합니다.
- 기준 10초는 설정값(기본 10초)입니다. 복귀 시작·도착·정지 이유는 Pi 5 로컬에 기록하고 연결되면 Supabase로 올립니다.
- 대시보드는 상태가 오지 않으면 "Pi 5 연결 끊김 — 마지막 수신 시각"을 크게 표시하고 명령 보내기를 막습니다(연결된 뒤 오래된 명령이 실행되지 않게).
- 쓰러진 사람 발견 시 로봇의 부저·자세 신호는 연결과 상관없이 그대로 합니다.
- **인터넷이 끊긴 동안은 대시보드의 전체 정지도 닿지 않습니다.** 현장 비상 정지 수단을 따로 둡니다 [사용자 결정 필요].
  후보는 Pi 5에 다는 물리 정지 버튼(누르면 Pi 5가 전체 정지)과 로봇 전원 스위치 끄기입니다.

## 1. 핵심 상태 (`dashboard/core`)

`DashboardCore(scenario, links, log)`가 시나리오 상태기계(`scenario/machine.py`), 로봇별 링크(`host/robot_link.RobotLink`),
사건 기록(`EventLog`, SQLite)을 묶습니다. 네트워크·웹 의존성이 없습니다.

| 조작 | 메서드 | 규칙 |
| --- | --- | --- |
| **전체 정지** | `estop_all()` | 확인 없이 바로. 모든 링크에 ESTOP을 걸고 즉시 한 번 보냄. 링크 하나·시나리오·기록이 실패해도 나머지는 계속하고, 실패 목록을 돌려줌(화면에 크게 표시) |
| 래치 해제 | `reset_latch(robot, confirmed=True)` | 확인 창을 거친 경우만. 신선한 래치 텔레메트리·배터리 조건은 링크가 검사. 실제 해제는 로봇 텔레메트리로 판단 |
| 알림 확인·안내 시작·재시도·조치 완료·순찰 시작·안내 재개 | `operator(event)` | 시나리오가 거부하면 `ok: False`와 이유 |
| 안내 멈춤 | `guide_blocked(reason)` | |

| 입력 | 메서드 | 처리 |
| --- | --- | --- |
| 링크 상태(10 Hz) | `update()` | 텔레메트리가 신선하고 래치가 풀리면 `robot_ready`. 끊기면 `link_lost`. **준비된 로봇이 스스로 래치되면**(저전압·감시 타이머 등) `robot_latched` 알림과 함께 준비 상태에서 뺌. 시나리오 시간 초과 처리 |
| 영상 감지 | `detection(result, zone)` | `host.vision.EvidenceMonitor` 결과. 알림 목록에 추가 |
| 도착 | `arrived(robot, target)` | 경로 실행 어댑터(D3)가 알림 |
| 카메라 수신 상태 | `camera_state(robot, state)` | `LatestFrameReceiver.state()`. 영상 없으면 `unknown` 표시 |

- 시나리오의 이동 명령(순찰·이동·안내·동작·자세)은 여기서 실행하지 않고 `drain_commands()`로 어댑터(D3)가 가져갑니다.
  `estop` 명령만은 어댑터를 기다리지 않고 바로 링크에 겁니다.
- `snapshot()`은 화면용 JSON(단계, 로봇 상태, 알림, 최근 알림 100개, 기록 실패 수)입니다.

## 2. 사건 기록 (`EventLog`)

- SQLite 한 표(`events`: 시각, 종류, 로봇, JSON 내용). 경로는 실행 시 지정, 기본은 메모리.
- 영상·사진 **바이트는 저장하지 않습니다**(`<bytes omitted>`로 바뀜). 필요하면 저장소 밖 로컬 경로 문자열만 남깁니다.
- 기록 실패는 예외 대신 실패 횟수로 알리며, 전체 정지 같은 조작을 막지 않습니다.
- 기록 파일은 현장 정보가 담기므로 저장소에 올리지 않습니다(`/logs/`, `outputs/`는 .gitignore).

## 3. 웹 서버와 화면 (`dashboard/web`)

표준 라이브러리만 씁니다(`http.server` + 200 ms JSON 폴링). 새 의존성이 없습니다.

```bash
python -m dashboard.web.run --sim                  # 가짜 로봇 A·B, http://127.0.0.1:8000
python -m dashboard.web.run --sim --host 0.0.0.0 --token <조작 토큰> --log D:\mechdog-logs\events.db
```

- `--sim` 또는 `--allow-real`을 명시해야 실행합니다. 실물 점검 어댑터는 한 소켓으로 두 로봇을 받고
  출처 주소·포트·로봇 ID를 대조합니다. 사용자가 대상 A/B를 승인한 뒤에만 아래 명령을 실행합니다.
  `python -m dashboard.web.run --allow-real --robot-a <A_IP> --robot-b <B_IP> --token <사용자 토큰>`
  실물 모드는 토큰이 필수입니다. HELLO/STOP/ESTOP과 사람이 확인한 RESET만 보냅니다.
  **순찰·경로·안내·동작·자세는 stationary_mode로 차단하고 정지합니다.** 경로 계획·실물 검증 전 이동하지 않습니다.
  시작·종료도 로봇으로 명령을 보내므로 에이전트는 이 명령을 실행하지 않습니다.
- 화면 맨 위 **전체 정지** 버튼은 확인 창 없이 바로 보내고, 실패하면 한 번 더 보낸 뒤 결과를 빨갛게 표시합니다.
- **전체 정지는 토큰 없이도** 받습니다(멈추는 쪽은 막지 않음). 순찰·안내 같은 조작과 래치 해제는 `--token`을 주면 토큰이 필요합니다.
- 래치 해제는 화면의 확인 창("주변이 안전하고 로봇을 지켜보고 있습니까?")을 거쳐야 하고, 서버도 `confirmed: true`만 받습니다.
- 서버와 연결이 끊기면 화면에 "정보가 오래됨"을 표시합니다. 로봇은 명령이 0.6초 끊기면 스스로 멈춥니다(규약 5.1절).
- 기본 주소는 127.0.0.1입니다. 관리자 노트북에서 열 때만 `--host`를 주고, 전용 공유기 안에서만 씁니다(HTTPS 아님).
- 이 화면은 **개발·시험용**입니다. 운영 대시보드는 0절의 Supabase 기준 구조로 새로 만듭니다.

## 4. 외부 배포 결정 (사용자, 2026-11-09) — 0절로 대체

> 0절 갱신에 따라 **대시보드는 인터넷으로 Supabase를 기준으로 동작**하고, Pi 5는 밖으로만 연결해 Supabase와 동기화합니다.
> 대시보드가 Pi 5에 직접 접속하지 않으므로 **cloudflared 터널은 필요 없습니다.** 아래 표는 기록으로 남기며, Supabase 행은 0.3절로 이어집니다.

| 항목 | 결정 | 할 일 |
| --- | --- | --- |
| 웹 서버 | **FastAPI + uvicorn** 사용 가능 | `dashboard/web/server.py`(현재 표준 라이브러리)를 FastAPI로 옮기고 화면 갱신은 WebSocket. 의존성은 `requirements-dashboard.txt`에 버전 고정·이유와 함께. `DashboardCore`·안전 규칙(전체 정지 토큰 없음, 래치 해제 확인)은 그대로 |
| 외부 접속 | **cloudflared**(Cloudflare Tunnel) | 대시보드는 계속 `127.0.0.1`에만 열고 cloudflared가 그 포트로만 연결. **Cloudflare Access(로그인) 필수**, 빠른 임시 터널(`--url`, 인증 없음)은 쓰지 않음. 카메라 스트림 포트·로봇 UDP·라이다 TCP는 터널에 넣지 않음 |
| 기록 DB | **Supabase**(Postgres) | `EventLog`와 같은 인터페이스(`record`/`recent`/`failures`)의 Supabase 판을 추가. **기록 실패·지연이 전체 정지를 막지 않게** 비동기 큐 + 로컬 SQLite 예비 기록 유지. 영상·사진 바이트는 올리지 않음 |

- Cloudflare 계정·터널 생성, Supabase 프로젝트·키 생성은 **사용자만** 합니다(비밀 정보). 키는 `.env`에만 두고 커밋하지 않습니다(`.env.example`에 이름만).
- 인터넷에 열리면 전체 정지 버튼도 인터넷에서 눌립니다. Access 로그인 뒤에만 열리게 하고, 로봇 쪽 정지(통신 끊김 0.6초)는 그대로 최종 안전 장치입니다.

## 5. Supabase 경유 노트북 처리와 Android 앱 알림 — 3단계, 명세만 (노트북 대시보드 완성 후)

알림 같은 데이터는 **Supabase DB에 모으고, 노트북 대시보드가 Supabase에서 받아 처리**합니다(사용자 결정, 2026-11-09).
Android 앱 알림도 노트북 대시보드가 맡습니다. **지금은 명세만 두고 개발하지 않습니다.** 1단계 노트북 대시보드가 완성된 뒤에 만듭니다.

```text
 Pi 5 (감지·알림 생성)
   │ sync_outbox 업로드 (0.3절)
   ▼
 Supabase DB ── alerts · robot_status · routine_runs · devices · notifications · commands
   │ 실시간 구독(노트북이 밖으로 연결)            ▲ 확인(ack)·처리 결과 기록
   ▼                                              │
 노트북 대시보드: 받기 → 처리(표시·등급·중복 묶기·재알림·발송) ──푸시(후보: FCM)──▶ Android 앱
                                                  ▲                                   │
                                                  └──────── 앱 "확인" ─────────────────┘
 Pi 5 ◀── ack를 commands 표에서 가져와 반영 (0.6절 명령 경로)
```

| 항목 | 명세 |
| --- | --- |
| 데이터 기준 | Supabase가 기준(0.3절). Pi 5가 올린 알림을 노트북이 **Supabase에서 받아** 처리합니다 |
| 노트북이 하는 처리 | Supabase 실시간 구독으로 새 알림·로봇 상태·순찰 결과를 받음 → 화면 표시, 등급 나누기, 같은 사건 묶기, 받는 사람 고르기, Android 푸시 발송, 확인 안 된 긴급 알림 재알림(간격은 설정값), 발송 결과를 Supabase `notifications`에 기록 |
| Android 앱 | 관리자용 최소 기능: 알림 표시·소리·진동, 알림 목록·로봇 상태·순찰 상태 보기(Supabase 읽기 전용 권한), "확인" 버튼 |
| 확인 처리 | 앱 "확인" → Supabase에 확인 기록 → 노트북 화면에 반영 → Pi 5가 0.6절 경로(`commands`, ack 명령)로 가져와 로컬 상태도 acked로. 누가 확인했는지 휴대폰 `device_id`로 남김 |
| 알림 내용 | 로봇 ID, 구역(확정 지도 기준, [mapping-and-patrol.md](mapping-and-patrol.md)), 시각, 종류(쓰러진 사람·래치·배터리·순찰 멈춤 등), 신뢰도, "확인 필요" 여부. **사진·얼굴·개인정보는 넣지 않음** |
| 종류·등급 | 긴급(쓰러진 사람, 로봇 래치) / 일반(배터리 낮음, 통신 끊김, 순찰 멈춤) / 정보 |
| 휴대폰 조작 범위 | 처음에는 **확인만**. 로봇을 움직이는 조작·래치 해제는 넣지 않음. 전체 정지를 넣을지는 인증·오작동 위험을 검토한 뒤 결정 |
| 인터넷 | Pi 5와 노트북 **둘 다** 인터넷 필요(0절과 같음). 노트북은 로봇망에 붙지 않으므로 어떤 인터넷이든 됨 |
| 인터넷이 없을 때 | Pi 5는 알림을 쌓아 두고 로봇을 서버 위치로 복귀·정지시킴(0.7절). 연결되면 쌓인 알림을 "지연됨" 표시와 함께 보냄 |
| 노트북이 꺼지면 | 휴대폰 알림은 오지 않음(Pi 5 감지·기록 업로드·안전 정지는 그대로). 휴대폰 알림을 안전 장치로 쓰지 않음 |
| 권한 | 0.4절 |
| 비밀 정보 | Supabase 키·푸시 서비스 키·기기 토큰은 각 기기의 로컬 비밀 설정에만, 저장소에 올리지 않음 |
| 계정·키 생성 | Supabase·Firebase 프로젝트, 앱 서명 키, 스토어 배포는 **사용자만** 합니다 |
| 담당 | 노트북 처리·Android 앱: 대시보드 담당(claude2, 현재 claude1 대행). Pi 5 업로드·ack 반영: codex1 |

- 전체 정지 같은 안전 조작도 대시보드에서는 Supabase를 거칩니다(0.6절). 휴대폰 알림은 안전 장치로 쓰지 않으며, 인터넷이 끊긴 동안의 현장 정지 수단은 0.7절을 따릅니다.

## 6. 확인하지 못한 것

- 실제 RobotLink·로봇과의 연결, 10 Hz 갱신에서의 지연, 장시간 SQLite 크기. D3 어댑터와 실물 시험에서 확인합니다.
- 대시보드 → Supabase → Pi 5 명령 지연(특히 전체 정지·정찰 조종), Supabase 요금제 한도 안에서 1초 상태 업로드가 되는지.
- 인터넷이 끊긴 동안의 현장 비상 정지 수단(0.7절, 사용자 결정).
- "끊길 것 같음" 판단 기준(텔레메트리 지연·손실률)과 서버 위치까지 복귀가 실제로 되는지.
- 사고 대응 중(발견 로봇 대기·안내 중)인 로봇에도 복귀 규칙을 똑같이 적용할지.
