# AI 작업 가이드

Claude Code, Codex, Copilot 같은 AI 에이전트가 이 저장소에서 작업할 때 따르는 규칙입니다.
사람이 읽어도 되지만, 기준은 "AI가 이것만 읽고 바로 올바르게 작업할 수 있는가"입니다.

## 1. 프로젝트 한 줄 요약

Mechdog Industry Safety는 Hiwonder MechDog 사족보행 로봇으로 산업 현장의 안전(순찰, 위험 감지, 알림)을
돕는 프로젝트입니다. 로봇은 **2대**이며, 시연 목표는 "쓰러진 사람을 카메라로 발견 → 대시보드로 관리자 알림 →
한 대가 관리자 위치로 가서 사고 지점까지 안내"입니다 → [시연 시나리오](../demo-scenario.md).
두 로봇은 같은 구성으로 **다리 4개, 앞쪽 비전 모듈(ESP32-S3 카메라), 팔 없음**이며
부가 서보(9·10번)에 연결된 장치도 없습니다. 로봇은 ESP32 + MicroPython으로 동작하며, **모든 제어는 Hiwonder 공식 MechDog
Python API**(`HW_MechDog`, `Hiwonder`, `Hiwonder_IIC`)로 합니다 → [MechDog 제어 API 규칙](mechdog-api.md).

이 저장소는 **claude1(로봇 쪽)과 codex1(Pi 5 호스트 쪽) 두 에이전트**가 각자 다른 작업 폴더에서 함께 작업합니다
→ [에이전트 협업 규칙](agents.md). 참고 자료는 기밀입니다 → [비공개 자료 규칙](confidentiality.md).

## 2. 구조

```text
(코드가 들어오면 실제 구조에 맞게 고칩니다. 괄호는 담당 에이전트)
docs/                  설계·개발 규칙 문서 (docs/protocol.md 는 claude1)
robot/                 MechDog 메인 ESP32에 올리는 MicroPython 코드, Hiwonder 공식 Python 기반 (claude1)
custom_sensors/        추가(비공식) 센서 읽기 드라이버. 센서 하나에 파일 하나 (claude1)
tools/bringup/         실물 확인용 REPL 스크립트 (claude1)
host/                  Raspberry Pi 5 쪽 Python: 라이다 수신, 로봇 명령, 카메라, 대시보드 (codex1)
ros2/                  ROS 2 실행 설정·노드 (codex1)
tools/mock/            가짜 로봇·가짜 라이다 서버 (codex1)
tools/hooks/           비공개 자료 커밋 방지 훅 (사용자)
tests/fakes/           HW_MechDog·Hiwonder·Hiwonder_IIC·machine 가짜 모듈 (claude1)
tests/robot/, tests/host/  각 쪽 자동 테스트 (실제 로봇 없이 돌아가야 함)
```

## 3. 반드시 지킬 것

0. **내가 claude1인지 codex1인지, 내 작업 폴더와 담당 영역이 맞는지 먼저 확인합니다.** [에이전트 협업 규칙](agents.md)대로
   작업 표시·충돌 확인·교차 리뷰를 합니다.
0. **참고한 외부 저장소·자료를 기록에 남기지 않습니다.** 이름·경로·코드·문구 모두 → [비공개 자료 규칙](confidentiality.md).
   커밋 훅(`tools/hooks`)을 끄거나 우회하지 않습니다.
0. **관절·이동·센서 등 모든 제어는 공식 MechDog API로만 합니다.** 직접 PWM·I2C·UART 구동, 자체 서보
   드라이버, 문서에 없는 메서드 사용 금지. 자세·동작은 문서의 포즈 목록에서 고릅니다
   → [MechDog 제어 API 규칙](mechdog-api.md).
   예외: 프로젝트에서 추가로 다는 **비공식 센서의 읽기 드라이버**는 `custom_sensors/`에 직접 작성합니다.
   이 드라이버는 로봇을 움직이지 않습니다(같은 문서 6절).
1. **실제 로봇을 사용자 확인 없이 움직이지 않습니다.** 로봇·모터·서보에 명령을 보내는 스크립트를
   실행하거나 펌웨어를 올리기 전에 반드시 사용자에게 묻습니다. 테스트는 하드웨어 없이(모의 객체,
   시뮬레이션) 돌아가게 작성합니다.
2. **정지·안전 로직을 약하게 만들지 않습니다.** 비상 정지, 통신 끊김 시 정지, 저전압 정지,
   관절 각도·속도 제한을 제거하거나 우회하지 않습니다. 바꿔야 한다면 PR에 이유를 분명히 적습니다.
3. **실패하면 안전한 쪽으로 멈춥니다.** 센서 값이 없거나 이상하면 "위험 없음"으로 처리하지 않고
   정지하거나 경고를 남깁니다. 모르는 값을 추측해서 정상처럼 다루지 않습니다.
4. **위험 감지 결과를 과장하거나 축소하지 않습니다.** 감지 신뢰도와 근거(어떤 센서, 어떤 임계값)를
   함께 남깁니다.
5. **비밀 정보를 커밋하지 않습니다.** Wi-Fi 비밀번호, API 키, 토큰은 `.env`나 로컬 설정 파일에 두고
   `.gitignore`로 제외합니다. 예시는 `.env.example`에 가짜 값으로만 씁니다.
6. **실제 현장 영상·사람 얼굴·작업자 정보를 커밋하지 않습니다.** 테스트 데이터는 코드로 생성하거나
   직접 만든 합성 데이터만 `tests/fixtures/**`에 둡니다. 파일 하나 10MB를 넘기지 않습니다.
7. **의존성은 꼭 필요할 때만 추가합니다.** 추가하면 PR에 이유를 적습니다.

## 4. 작업 절차

0. 열린 PR·원격 브랜치를 확인해 다른 에이전트와 겹치는 작업인지 봅니다(`gh pr list`, `git branch -r`).
1. 브랜치: [브랜치 규칙](branch-rules.md). `feat/<설명>` 또는 `issue/<번호>-<설명>`. `main`에 직접 커밋 금지.
2. 구현 전에 비슷한 기존 코드를 찾아 같은 방식으로 작성합니다.
3. 테스트 추가 → 전체 테스트 실행:
   ```bash
   python -m unittest discover -s tests
   ```
   (테스트 도구가 바뀌면 이 명령을 갱신합니다.)
4. 실제 로봇에서 확인이 필요한 변경은 사용자에게 확인을 요청하고, 확인하지 못했으면 PR에 그렇게 씁니다.
5. 커밋: `feat:`/`fix:`/`docs:`/`test:`/`refactor:`/`chore:` + **한국어 요약**, 본문에 한국어 설명. 본문 끝에 `Agent: claude1`/`Agent: codex1`.
   사용자가 커밋을 에이전트에게 맡겼으므로 작업 단위가 끝나면 따로 묻지 않고 커밋합니다(푸시·PR은 별도 확인).
6. PR: 첫 줄에 `작업자: claude1`/`codex1`, 제목 앞에 `[claude1]`/`[codex1]`, 템플릿을 채우고 [코드 리뷰 규칙](code-review.md)의 체크리스트를 스스로 먼저 점검합니다.
7. 결과 보고: 무엇을 했는지, **검증하지 못한 것**(예: 실제 로봇 동작, 현장 조명·소음 환경)을 숨기지 않고 적습니다.

## 5. 자주 하는 작업

### 버그 수정 (`issue/` 브랜치)

1. 이슈의 재현 조건을 테스트로 만들어 실패를 확인합니다.
2. 원인을 고치고(증상만 가리지 않기) 테스트 통과를 확인합니다.
3. PR 본문에 `Fixes #번호`.

## 6. AI 코드 리뷰를 할 때

- 다른 에이전트의 PR을 리뷰합니다(claude1 ↔ codex1). 승인은 `[내 이름] 리뷰: 승인` 코멘트로 하고, 병합은 조건을 채운 뒤 PR 작성자가 합니다
  ([에이전트 협업 규칙](agents.md) 6절). 자기 PR을 스스로 승인하지 않습니다.
- [코드 리뷰 규칙](code-review.md)의 우선순위(물리 안전 → 공식 API 사용 → 감지 정확성 → 보안 → 테스트 → 품질) 순서로 봅니다.
- 지적마다 `[차단]/[제안]/[사소]/[질문]` 접두어, 파일:줄, **구체적인 실패 상황과 결과**를 씁니다.
- 직접 확인하지 못한 추측은 `[질문]`으로 낮춥니다. 스타일 지적으로 중요한 문제를 묻히지 않게 합니다.
- 문제가 없으면 "차단 사유 없음"이라고 분명히 씁니다.
