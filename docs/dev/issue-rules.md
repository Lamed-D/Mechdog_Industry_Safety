# 이슈 규칙

GitHub Issues로 버그와 기능 요청을 관리합니다. 이슈를 만들 때는
`.github/ISSUE_TEMPLATE`의 템플릿을 사용합니다.

## 종류와 라벨

| 템플릿 | 제목 형식 | 라벨 | 작업 브랜치 |
| --- | --- | --- | --- |
| 버그·오류 (`issue.md`) | `[issue] <무엇이 잘못되는지>` | `issue` | `issue/<번호>-<설명>` |
| 기능 요청 (`feat.md`) | `[feat] <무엇을 하고 싶은지>` | `feat` | `feat/<설명>` |

추가 라벨(선택): `safety`(정지·제한 로직), `motion`(걸음새·자세), `sensor`(공식 센서·감지),
`custom-sensor`(추가로 다는 비공식 센서),
`comm`(Wi-Fi·원격 제어), `docs`, `good first issue`.

## 좋은 이슈의 조건

- **재현 가능해야 합니다.** 버그는 무엇을 실행했는지(스크립트·명령), 로봇 상태(배터리, 자세, 바닥),
  실제 결과와 기대 결과를 적습니다.
- **오류 메시지는 전체를 붙입니다.** 시리얼 출력, traceback, 로그.
- **환경을 적습니다.** 로봇 펌웨어 버전, PC OS, Python 버전, 연결 방식(USB/Wi-Fi).
- **안전 문제는 제목에 표시합니다.** 로봇이 멈추지 않거나 예상 밖으로 움직였다면 `safety` 라벨을 붙이고
  우선 처리합니다.
- 한 이슈에는 한 가지 문제만 적습니다.

## 현장 데이터 주의 (중요)

- **작업자 얼굴이 나온 영상·사진, 실제 현장 위치·회사 정보를 이슈에 첨부하지 않습니다.**
  필요하면 가리거나 재현용으로 새로 찍은 자료를 씁니다.
- Wi-Fi 비밀번호, 토큰이 들어간 설정 파일·로그는 해당 값을 지우고 붙입니다.

## 처리 흐름

1. 이슈 생성 → 라벨 지정
2. 담당자가 브랜치 생성: `issue/<번호>-<설명>` 또는 `feat/<설명>`
3. PR 본문에 `Fixes #번호`(버그) / `Closes #번호`(기능)
4. PR 병합 시 이슈 자동 종료

버그를 고칠 때는 **그 버그를 재현하는 테스트를 먼저 추가**하고, 테스트가 실패하는 것을
확인한 뒤 수정합니다.
