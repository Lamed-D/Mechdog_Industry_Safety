# 코드 리뷰 규칙

모든 변경은 PR로 `main`에 들어가며, 병합 전에 리뷰를 받습니다.
사람 리뷰어와 AI 리뷰어 모두 이 문서를 기준으로 봅니다.

## PR 작성자

- PR 제목은 커밋 메시지 형식(`feat: ...`, `fix: ...`)으로 씁니다. squash merge 시 이 제목이 커밋이 됩니다.
- PR 템플릿의 체크리스트를 채웁니다: 무엇을/왜, 관련 이슈, 테스트 방법, 실제 로봇 확인 여부.
- PR은 작게 유지합니다. 400줄 이상 변경이면 나눌 수 있는지 먼저 검토합니다.
- 리뷰 요청 전에 직접 확인합니다:
  ```bash
  python -m unittest discover -s tests
  ```

## 리뷰 우선순위

위에서부터 중요합니다. 위 항목에 문제가 있으면 아래 항목(스타일 등)보다 먼저 지적합니다.

### 1. 물리 안전 (차단 사유)

- 비상 정지, 통신 끊김 시 정지, 저전압 정지가 유지되는지. 어떤 코드 경로에서도 우회되지 않는지.
- 관절 각도·속도·토크 제한이 지켜지는지. 새 동작(걸음새, 자세)이 제한 밖 값을 보내지 않는지.
- 예외·타임아웃이 나면 로봇이 **멈추는 쪽**으로 끝나는지(마지막 명령을 계속 유지하지 않는지).
- 사용자 확인 없이 실제 하드웨어를 움직이는 코드가 테스트·스크립트에 들어오지 않았는지.

### 2. 공식 MechDog API 사용 (차단 사유)

- 관절·이동·자세·센서·출력 제어가 모두 `HW_MechDog.MechDog`, `Hiwonder`, `Hiwonder_IIC`를 통하는지
  ([MechDog 제어 API 규칙](mechdog-api.md)).
- `machine.PWM`·raw I2C·UART로 하드웨어를 직접 구동하거나 자체 서보 드라이버를 만들지 않았는지.
  `machine` 직접 사용은 `custom_sensors/`의 추가 센서 읽기에만 허용됩니다.
- 추가 센서 드라이버가 로봇을 움직이지 않고, 실패 시 `None`을 돌려주며, 읽기에 시간 제한이 있는지.
  배선 표(mechdog-api.md 6.3절)가 같은 PR에서 갱신됐는지.
- 자세·동작이 포즈 목록(4절)에 있는 것인지. "시연 전용" 동작을 현장 기능에 쓰면 이유가 있는지.
- 문서에 없는 메서드·인자를 지어내지 않았는지, 값이 문서 범위 안인지(예: `move` step -100~100).
- 우리 로봇에 없는 장치(팔·집게·꼬리 등, `set_servo`)를 쓰는 코드가 없는지(mechdog-api.md 0절).
- 정지는 `mechdog.move(0, 0)`이고, 예외·종료 경로(`finally`)에서 호출되는지.

### 3. 감지 정확성 (차단 사유)

- 센서 값이 없거나 범위를 벗어나면 "정상/위험 없음"으로 처리하지 않는지.
- 임계값·단위(°C, ppm, cm 등)가 맞는지, 하드코딩된 값에 근거가 적혀 있는지.
- 감지 결과에 신뢰도·근거가 함께 남는지. 추측을 확정처럼 알리지 않는지.

### 4. 보안·개인정보

- 비밀 정보(Wi-Fi 비밀번호, API 키, 토큰)가 코드·로그·커밋에 들어가지 않았는지.
- 원격 제어 경로에 인증 없이 로봇을 움직일 수 있는 입구가 생기지 않았는지.
- 카메라 영상·작업자 정보가 필요 이상으로 저장·전송되지 않는지.

### 5. 테스트

- 새 기능에는 하드웨어 없이 도는 테스트(모의 객체, 합성 센서 데이터)가 있는지.
- 버그 수정에는 그 버그를 재현하는 테스트가 있는지.
- 테스트 데이터가 생성 코드로 다시 만들어지고(`tests/fixtures/**`), 실제 현장 자료가 섞이지 않았는지.

### 6. 코드 품질

- 주변 코드와 같은 스타일(짧은 함수, 과하지 않은 주석)인지.
- 새 의존성이 꼭 필요한지, PR에 이유가 있는지.
- 매직 넘버(핀 번호, 서보 각도, 임계값)는 이름 있는 상수나 설정으로 모았는지.

## 리뷰 코멘트 형식

코멘트 앞에 심각도를 붙입니다.

| 접두어 | 의미 | 병합 |
| --- | --- | --- |
| `[차단]` | 물리 안전·비공식 제어 경로·감지 오류·보안·테스트 실패 | 고치기 전 병합 불가 |
| `[제안]` | 더 나은 구현, 누락된 경계 처리 | 작성자가 판단, 답변 필요 |
| `[사소]` | 이름, 오타, 스타일 | 선택 |
| `[질문]` | 의도 확인 | 답변 필요 |

- 문제와 함께 **구체적인 실패 상황**(어떤 입력·상황에서 무엇이 잘못되는지)과 가능하면 수정안을 적습니다.
- 확인하지 않은 추측은 `[질문]`으로 씁니다.

## 병합 조건

- 상대 에이전트의 `리뷰: 승인` 코멘트(claude1 ↔ codex1, 마지막 커밋 이후). 병합은 PR 작성자가 직접 합니다([에이전트 협업 규칙](agents.md) 6절)
- 공용 규칙·설정 파일을 바꾸는 PR은 사용자 승인 후 병합
- `[차단]` 코멘트 모두 해결
- 전체 테스트 통과
- 동작이 바뀌는 변경은 실제 로봇 확인 여부를 PR에 기록
- squash merge, 병합 후 브랜치 삭제
