# 장착 비전 모듈과 호스트 감지 경계

## 사용자 확인 결과

구입 당시 펌웨어에서 휴대폰 Wi-Fi `HW_ESP32S3CAM` 연결 후 `http://192.168.5.1/`의 Image 화면으로
실시간 영상 표시가 성공했습니다. 원본 영상 사용을 우선하며 인식용 펌웨어로 바꾸지 않습니다.
공식 IIC 얼굴 호출은 face_read/errno19로 실패했습니다. 두 결과는 별도 기능으로 기록합니다.
PC/Pi 스트림 수신 URL·두 대 동시 연결·추론·낙상 정확도는 아직 미검증입니다. 영상 파일은 저장하지 않았습니다.
공식 절차: [제조사 영상 안내](https://docs.hiwonder.com/projects/ESP32-S3/en/latest/docs/3.Image_Recognition_Course.html).

카메라는 장착된 ESP32-S3 모듈을 사용합니다. MechDog 공식 Hiwonder Python 연결은
`robot/vision.py`의 `ESP32S3Cam(IIC(2))`이며 최신 제조사 얼굴 예제의 `read_face()`를 우선 사용합니다.
이전 메서드만 있는 장치에서는 `face_recognition()`을 사용하고 결과 유형·존재만 진단합니다.
제조사 연결 그림의 본체 물리 IIC 포트 1이 코드 IIC(2)에 대응합니다.
메인 보드와 비전 보드의 펌웨어는 다릅니다. 카메라를 다른 보드로 교체하거나 Arduino로 전환하는 절차가 아닙니다.

## 맞춤 카메라 펌웨어 수신

[맞춤 펌웨어](vision-cam-firmware.md)를 올리면 카메라가 전용 공유기에 붙고 Pi 5는 `host/vision/camera_client.py`로
`/status`, `/capture`, `:81/stream`(최신 프레임만)을 받습니다. 형식과 신선도 규칙은 [통신 규약 11절](protocol.md#11-비전-모듈-맞춤-펌웨어-영상i2c).
오래되거나 끊긴 영상은 `unknown`이며 "사람 없음"이 아닙니다. 영상은 메모리에만 둡니다.

## 현재 실행 가능 범위

- PC: `python -m unittest discover -s tests`로 합성 관측·오류·무응답·신선도 검증.
- 사용자 승인 후 MechDog: [본체·카메라 읽기 점검](user-tests/current-hardware.md).
- Pi·실제 영상 추론: 대기. 원본 영상의 지원 경로·주소·형식은 사용자 확인이 필요합니다.

공식 얼굴·색 인식 결과는 원본 프레임이나 낙상 자세 정보가 아닙니다.
얼굴 검출 성공을 쓰러진 사람 검출로 보고하지 않습니다. HTTP 경로를 추측하거나 공식 I2C 장치를 raw 드라이버로 읽지 않습니다.

`host/vision/evidence.py`는 추론 어댑터가 제공하는 후보·신뢰도·취득 시각을 검증하고 지속된 의심 이벤트를 만듭니다.
기본 임계 0.8·지속 2초·허용 간격 0.5초는 실측 전 가정입니다. 단일 프레임·낮은 신뢰도는 확인 필요,
오류·오래된 관측·미래 시각·중복·소스 단절은 unknown입니다. 위험 없음으로 바꾸지 않습니다.
이 모듈 자체는 이미지를 추론하지 않습니다. 실제 모델은 아직 선정·설치하지 않았으며 실제 낙상 감지 기능은 미완료입니다.

## 최신 프레임 추론 작업자

`host/vision/pipeline.py`의 `VisionPump`는 A/B 수신기를 받아 한 프레임씩 모델에 넘깁니다.
모델 함수는 JPEG를 실제 디코딩·전처리한 뒤 `{"candidate": bool, "confidence": float}`를 반환해야 합니다.
사람 자세·낙상 판단 근거를 제공하는 모델 어댑터이며 단순 얼굴 검출 함수로 대체하지 않습니다.
`source="model"` 또는 합성 시험의 `source="synthetic"`을 명시합니다. 모델이 없으면 infer=None으로 unknown을 반환합니다.

- 수신 스레드와 별도 추론 작업자를 사용합니다. 처리 중 새 프레임은 수신기의 최신 한 장을 덮어쓰며 큐를 만들지 않습니다.
- 같은 순번·취득 시각은 다시 추론하지 않습니다. 두 로봇의 시간 창은 분리합니다.
- SOF 해상도 640×480 미만·잘린 헤더·모델 오류·500ms 이상 늦은 결과는 unknown입니다.
  SOF 검사는 실제 JPEG 디코딩을 대신하지 않습니다. 모델 자체에도 디코딩 실패 처리가 필요합니다.
- `pump.start()`는 모델을 작업 스레드에서 호출합니다. `RobotAdapter(..., vision=pump)`의 제어 루프에서는
  `pump.apply(core)`로 완료 결과만 읽고 모델·네트워크 요청을 호출하지 않습니다.
- 모델이 오래 막혀도 제어 루프에서 취득 시각을 다시 확인해 오래된 판단을 unknown으로 바꿉니다.
  Python 스레드의 강제 종료는 제공하지 않습니다. 모델 프로세스 격리가 필요한지는 Pi 실측 후 결정합니다.
- `snapshot()`에는 처리 수·오류 수·최근 최대 200회의 추론 시간 p95와 판단 메타데이터만 있습니다.
  JPEG·얼굴·사진은 결과나 로그로 복사하지 않습니다.

영상·추론이 unknown이면 순찰뿐 아니라 호출·안내·복귀 중 해당 로봇도 정지합니다.
호출·안내는 suspended로 옮기고 영상이 돌아온 것만으로 재개하지 않습니다. 정상 근거가 돌아온 뒤 사람이 재시도합니다.
현재 고정 위치 어댑터는 여전히 이동·자세를 차단하므로 이 연결만으로 실물 주행이 켜지지 않습니다.

## 모델 연결 전 필요한 사용자 결과

추론 작업자는 모델 호출 전에도 프레임의 A/B ID·순번·유한 취득 시각·JPEG 형태·크기·나이를 검사합니다.
이미 늦었거나 미래인 프레임은 모델에 넣지 않아 다른 로봇의 최신 영상 처리 시간을 낭비하지 않습니다.
잘못된 프레임 객체와 수신 상태는 unknown이며, 이 사전 검사는 실제 JPEG 디코딩 성공을 대신하지 않습니다.

모델 후보·라이선스·장비 차이와 검증 기준은 [영상 모델 계획](fall-detection-plan.md)에 정리했습니다.

1. 공식 Python 카메라 초기화·읽기 결과·현재 기능 모드·호출 시간.
2. 장착 모듈의 원본 프레임 제공 방식과 해상도·fps·전원 상태. 얼굴 영상은 게시하지 않습니다.
3. Pi 수령 후 두 스트림 동시 디코딩·추론 CPU/메모리/온도/지연.
4. 모델 라이브러리와 가중치의 라이선스·배포 조건, 합성/대체물 기반 오탐·미탐·신뢰도 측정.

확인 전에는 synthetic 관측만 scenario와 연결합니다. 실물 데이터와 합성 이벤트의 source를 혼합하지 않습니다.
영상·얼굴·사진은 저장하지 않습니다. 사건에는 로봇·시각·신뢰도·임계·소스·확인 필요 상태만 남깁니다.
MQTT를 적용해도 제어 토픽에 영상을 싣지 않으며 세션·만료·신선도 검증을 유지합니다.
