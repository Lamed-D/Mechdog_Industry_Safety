# 지도 작성 → 지도 확정 → 구역 지정 → 순찰 루틴

로봇을 새 현장에 처음 두었을 때부터, 매일 순찰을 반복하기까지의 운영 흐름입니다(사용자 결정, 2026-11-09).
**대시보드 작업(①~③의 사람 조작, ④의 루틴 설정)은 인터넷으로 Supabase를 거칩니다**([dashboard.md](dashboard.md) 0절).
**④ 순찰 루틴의 실행은 Pi 5가 합니다. 연결이 10초 이상 끊기거나 끊길 것 같으면 순찰을 멈추고 서버 위치로 돌아가 정지합니다**([dashboard.md](dashboard.md) 0.7절).
기기 역할은 [dashboard.md](dashboard.md) 0절, 사고 대응은 [시연 시나리오](demo-scenario.md)를 따릅니다.

## 1. 전체 흐름

```text
① 정찰·지도 작성   로봇이 라이다로 현장을 돌며 Pi 5가 지도 초안을 만듦
        │
        ▼
② 지도 검토·확정   사람이 대시보드에서 초안을 보고 다듬어 확정
        │          (선택) 노트북의 이미지 생성 모델로 정리한 제안본을 비교해 반영
        ▼
③ 구역·지점 지정   확정 지도 위에 순찰 구역, 금지 구역, 지점, 순찰 경로를 그림
        │
        ▼
④ 순찰 루틴       Pi 5가 시간표대로 로봇에게 순찰을 시킴(연결이 끊기면 서버 위치로 복귀 후 정지)
        │
        └─ 순찰 중 쓰러진 사람 발견 → 사고 시나리오가 루틴보다 우선 → 조치 완료 후 루틴 재개
```

| 단계 | 하는 곳 | 사람 할 일 | 결과물(Supabase 기준, Pi 5 로컬 사본) |
| --- | --- | --- | --- |
| ① 정찰·지도 작성 | Pi 5(SLAM), 로봇 | 대시보드에서 로봇을 천천히 몰거나 정찰 시작·멈춤 | 지도 초안(`draft`) |
| ② 지도 검토·확정 | 노트북 대시보드, (선택) 노트북 이미지 모델 | 초안과 현장을 비교해 다듬고 확정 버튼 | 확정 지도(`confirmed`, 버전 고정) |
| ③ 구역·지점 지정 | 노트북 대시보드 | 확정 지도 위에 구역·지점·경로 그리기 | 구역·지점·경로 |
| ④ 순찰 루틴 | Pi 5(일정·경로 계획·감지) | 루틴 만들기·켜기/끄기, 알림 처리 | 루틴 실행 기록, 알림 |

## 2. ① 정찰·지도 작성

- **지도는 Pi 5가 만듭니다.** 로봇 등 위 라이다 스캔(원시 TCP 중계, [lidar-integration.md](lidar-integration.md))을 받아 ROS 2 SLAM으로 2D 점유 격자 지도를 만듭니다.
  SLAM 패키지는 ROS 2 Jazzy의 `slam_toolbox`를 1순위 후보로 둡니다(호스트 담당이 확정).
- **로봇의 이동 거리(오도메트리)를 읽는 공식 API가 없습니다.** 그래서 라이다 스캔끼리 맞춰 움직임을 추정하는 방식(레이저 오도메트리)을 후보로 둡니다
  [실물 확인 필요]. 걷는 진동과 테이프 고정 때문에 바퀴 로봇보다 지도가 덜 깔끔할 수 있습니다.
- **처음 방식은 사람이 모는 정찰입니다.** 노트북 대시보드에서 로봇을 낮은 속도로 직접 몹니다(명령은 Supabase를 거쳐 Pi 5로, [dashboard.md](dashboard.md) 0.6절).
  - 조종 명령도 Pi 5를 거쳐 기존 `CMD` 규약([protocol.md](protocol.md))으로 갑니다. 보폭·회전은 작은 값으로 제한합니다(공식 범위 안, [mechdog-api.md](dev/mechdog-api.md) 3절).
  - 버튼을 누르고 있는 동안만 움직입니다(손을 떼거나 화면이 끊기면 정지). 로봇 쪽 0.6초 통신두절 정지는 그대로입니다.
  - 직접 조종 명령은 **지도 작성 모드에서만** 받고, 명령마다 유효 0.5초입니다. 새 명령이 없으면 Pi 5가 멈춥니다. 인터넷 지연이 크면 자주 멈출 수 있으며, 조종하는 사람은 로봇을 눈으로 볼 수 있는 곳에 있어야 합니다.
- 미탐색 영역을 찾아 스스로 돌아다니는 자동 정찰(프런티어 탐색)은 사람이 모는 정찰이 안정된 뒤의 후순위입니다.
- 지도는 **한 대(보통 로봇 A)로 먼저** 만들고, 두 로봇이 같은 확정 지도를 씁니다. 두 대 지도 합치기는 하지 않습니다(처음 범위 밖).
- 정찰 중에도 쓰러진 사람 감지·장애물 정지·전체 정지는 그대로 켜 둡니다.

## 3. ② 지도 검토·확정 (사람 + 대시보드)

1. 정찰이 끝나면 Pi 5가 초안을 만들어(점유 격자 이미지 + 해상도·원점 정보. ROS 2 지도 서버 형식인 PGM + YAML 후보) Supabase 비공개 파일 저장소에 올립니다.
2. 대시보드에 초안을 띄우고, 사람이 현장과 비교해 다듬습니다.
   - 벽 잡음·떠다니는 점 지우기, 유리·거울처럼 라이다가 못 본 벽을 선으로 그려 넣기, 빈 곳 메우기 금지 구역으로 막기.
3. **(선택) 노트북 이미지 생성 모델로 정리:** 초안 이미지를 노트북에서 돌리는 모델에 넣어 벽을 곧게 하고 잡음을 지운 **제안본**을 만듭니다.
   - 모델은 **노트북 로컬에서만** 돌립니다. 현장 배치도가 되는 지도를 Supabase 말고 다른 외부 서비스로 보내지 않습니다. 모델 파일은 저장소에 올리지 않습니다.
   - 제안본은 초안과 **같은 크기·해상도·원점**이어야 합니다. 다르면 Pi 5가 받지 않습니다.
   - 제안본은 **절대 자동으로 확정되지 않습니다.** 대시보드가 초안과 겹쳐 보여 주고, 사람이 보고 반영할지 고릅니다.
   - **안전 규칙(Pi 5가 검사):** 초안에서 **모르는 칸을 빈 칸(갈 수 있음)으로 바꾸는 것은 거부**합니다.
     장애물 칸을 빈 칸으로 바꾼 곳은 따로 표시해, 사람이 그 부분을 하나씩 승인해야 반영됩니다. 장애물을 더하는 쪽은 그대로 허용합니다.
   - 모델을 쓰지 않아도 ②단계는 사람이 손으로 다듬어 끝낼 수 있습니다. 모델 종류는 정하지 않았습니다.
4. 사람이 **확정**을 누르면 Supabase에서 그 지도는 버전이 고정되고(`confirmed`), 이후 구역·경로·루틴은 이 버전을 가리킵니다.
   Pi 5는 확정 지도를 내려받아 위 안전 규칙과 해시를 다시 검사한 뒤 로컬 사본으로 씁니다. 검사에 실패하면 쓰지 않고 대시보드에 이유를 올립니다.
   - 확정 기록: 누가(기기 `device_id`), 언제, 초안 버전, 반영한 제안본 여부, 파일 해시.
   - 현장이 바뀌어 지도를 다시 만들면 새 버전이 되고, 옛 버전에 묶인 구역·루틴은 **사람이 새 지도에서 다시 확인할 때까지 실행하지 않습니다.**

## 4. ③ 구역·지점 지정

확정 지도 위에서 대시보드로 그립니다. 좌표는 지도 좌표(m)로 Supabase에 저장하고, Pi 5가 가져가 검사한 뒤 로컬 사본으로 씁니다.

| 종류 | 모양 | 쓰임 |
| --- | --- | --- |
| 순찰 구역 | 다각형 | 이름(예: "A동 통로"). 알림에 "어느 구역"으로 표시 |
| 금지 구역 | 다각형·선 | 로봇이 들어가지 않음(경로 계획에서 막음). 계단·낭떠러지·기계 주변 등 |
| 감속 구역 | 다각형 | 작은 보폭·느린 걸음새로만 지남 |
| 지점 | 점 + 방향 | 출발·대기 위치, **관리자 위치**(사고 시나리오에서 로봇 B가 가는 곳), **서버 위치**(Pi 5 근처 복귀 지점, 연결이 끊기면 돌아오는 곳), 점검 지점 |
| 순찰 경로 | 지점의 순서 | 지점마다 머무는 시간, 할 일(멈춰서 카메라로 둘러보기 등 공식 동작 안에서) |

- 출발·대기 위치, 관리자 위치, 서버 위치는 확정 지도마다 **반드시 하나씩** 있어야 루틴을 켤 수 있습니다.
  서버 위치는 Pi 5 핫스팟 신호가 잘 닿는 Pi 5 가까운 곳에 둡니다.
- 경로가 금지 구역을 지나거나, 지점이 지도 밖·장애물 위에 있으면 대시보드가 저장 전에 막고, Pi 5도 가져올 때 다시 검사해 거부합니다.

## 5. ④ 순찰 루틴 (Pi 5에서 실행)

루틴 = **어느 로봇이 · 어느 경로를 · 언제 · 어떤 조건으로** 도는지.

| 항목 | 내용 |
| --- | --- |
| 시간표 | 수동 시작 / 매일 정해진 시각 / 일정 간격 반복. 로봇 두 대 번갈아 돌기 가능 |
| 시작 전 확인 | 로봇 연결과 텔레메트리 최신, 배터리 기준 이상, 래치·전체 정지 없음, 자기 위치 신뢰도 기준 이상, 확정 지도 버전 일치. 하나라도 아니면 시작하지 않고 대시보드에 이유 표시 |
| 실행 | Pi 5가 확정 지도에서 자기 위치를 잡고(위치 추정), 경로 계획(ROS 2 Nav2 후보)으로 지점을 차례로 감. 계획 결과는 호스트에서 공식 `move(step, angle)` 범위로 바꿔 보냄 |
| 도는 중 멈춤 | 자기 위치를 잃음, 장애물, 통신 끊김, 센서 값 없음 → 정지하고 알림. 스스로 다시 출발하지 않고 사람 확인 후 재개 |
| 연결 끊김 | 인터넷 10초 이상 끊김, 또는 로봇망이 약해져 끊길 것 같음 → 루틴 일시 정지 → 서버 위치로 복귀 → 그래도 안 되면 서버 근처에서 정지([dashboard.md](dashboard.md) 0.7절). 연결이 돌아와도 사람이 재개 명령을 보내야 다시 순찰 |
| 사고 발생 | 쓰러진 사람 감지 → 루틴 일시 정지, 사고 시나리오가 우선(발견 로봇 대기, 다른 로봇이 관리자 위치로). "조치 완료" 뒤 루틴을 이어 하거나 대기 위치로 복귀(루틴 설정) |
| 전체 정지 | 모든 루틴 즉시 정지. 다시 켜는 것은 사람만 |
| 기록 | 시작·지점 도착·멈춤 이유·종료를 Pi 5 로컬에 먼저 쓰고 Supabase로 올림(`robot_id`·`device_id` 포함) |

- **루틴 설정은 Supabase가 기준**이고, Pi 5는 가져온 사본으로 실행합니다. 노트북이 꺼져 있어도 Pi 5가 인터넷에 연결돼 있으면 루틴은 시간표대로 돕니다.
  인터넷이 끊기면 위 "연결 끊김" 규칙대로 서버 위치로 돌아가 정지합니다. 끊긴 동안의 기록·알림은 Pi 5에 쌓였다가 연결되면 올라갑니다.
- **시각 주의:** Pi 5는 인터넷이 없으면 시간 맞추기(NTP)를 못 하고, RTC 배터리가 없으면 재부팅 뒤 시각이 틀어집니다.
  평소에는 인터넷으로 시각을 맞추고, 끊긴 뒤 재부팅에 대비해 RTC 배터리를 다는 것을 권합니다(사용자 결정, 비용).

## 6. 저장 (Supabase 기준 + Pi 5 로컬 사본)

[dashboard.md](dashboard.md) 0.3절의 Supabase 기준 DB에 다음 표를 더하고, Pi 5는 실행에 필요한 확정 버전만 로컬 사본으로 둡니다.
지도 이미지는 Supabase **비공개** 파일 저장소에 두고 표에는 경로·해시만 기록합니다. Pi 5 사본은 로컬 폴더(예: `/var/lib/mechdog/maps/<지도ID>/`)에 둡니다.

| 표 | 내용 |
| --- | --- |
| `maps` | 지도 ID, 버전, 상태(`draft`→`confirmed`→`archived`), 해상도·원점, 파일 경로·해시, 만든·확정한 기기와 시각, 반영한 제안본 여부 |
| `zones` | 지도 버전, 종류(순찰·금지·감속), 이름, 다각형 좌표 |
| `waypoints` | 지도 버전, 종류(출발·대기·관리자 위치·서버 위치·점검), 좌표·방향 |
| `routes` | 지점 순서, 지점별 머무는 시간·할 일 |
| `routines` | 로봇, 경로, 시간표, 시작 조건, 켜짐 여부 |
| `routine_runs` | 실행마다 시작·끝·멈춤 이유·결과 |

- 실제 현장 지도는 현장 배치 정보이므로 **저장소에 커밋하지 않습니다.** 테스트용 지도는 코드로 만든 합성 지도만 `tests/fixtures/`에 둡니다.

## 8. 확인하지 못한 것

- 걷는 로봇 + 테이프 고정 라이다 + 오도메트리 없음 조건에서 SLAM 지도 품질과 위치 추정 안정성 [실물 확인 필요]
- 정찰에 알맞은 보폭·회전 값, 지도 한 장을 만드는 데 걸리는 시간
- 두 로봇이 같은 지도에서 동시에 위치를 잡을 때 Pi 5 부하
- 지도 정리에 쓸 노트북 이미지 모델 종류와 정리 품질
- 인터넷 경유 정찰 조종의 지연과 조종감
- Pi 5 RTC 배터리 장착 여부
