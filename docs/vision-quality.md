# Pi 5 모델 입력용 화질·전송 기준

같은 장비를 갖춘 로봇 A/B 각각의 카메라 → 전용 공유기 → 고정 Pi 5 16GB를 기준으로 합니다.
A/B는 고정 식별자이며 주 역할·대기 역할은 통신으로 별도 결정합니다. **아래 FPS는 목표 상한이며 실측 결과가 아닙니다.**
Pi의 RAM 용량만으로 모델 추론 속도나 낙상 감지 정확도를 보장할 수 없습니다.

## 조사한 사실

- 제조사 카메라 예제의 JPEG 품질 설정은 16입니다. 해상도·버퍼 수는 호출자가 넘기는 형태도 있습니다.
- 순정 영상 펌웨어의 읽을 수 있는 문자열에서는 JPEG·스트림·캡처와 여러 센서 지원을 확인했습니다.
  **실제로 선택되는 센서·기본 해상도·JPEG 품질·FPS는 문자열만으로 확인하지 못했습니다.** 역컴파일하지 않았습니다.
- 공식 카메라 드라이버는 JPEG 품질 수가 작을수록 OV 계열의 압축을 줄입니다. VGA 이상의 안정적 사용에는 PSRAM을 전제합니다.
  [공식 드라이버 안내](https://github.com/espressif/esp32-camera/blob/master/README.md),
  [공식 설정·취득 시각 정의](https://github.com/espressif/esp32-camera/blob/master/driver/include/esp_camera.h).

## 제공하는 설정

| 프로필 | 전송 해상도 | JPEG 품질 | 최대 전송용 프레임 | 용도 |
| --- | --- | --- | --- | --- |
| balanced (기본) | 640×480 | 10 | 약 15fps/대 | 두 대 동시 수신·가벼운 사람/자세 모델의 시작값 |
| detail | 800×600 | 10 | 약 10fps/대 | 작은 사람 윤곽·원거리 세부 확인; 대역·디코딩 비용 증가 |
| PSRAM 인식 실패 | 320×240 | 10 | 프로필 상한 이내 | 진단용, 모델용 화질 합격으로 보지 않음 |

센서 실제 FPS가 낮으면 상한까지 올라가지 않습니다. 조명이 어두우면 노출 때문에 흔들림·지연이 늘 수 있습니다.
카메라 XCLK는 제조사 근거가 있는 15MHz를 유지하며 속도를 위해 임의로 올리지 않습니다.
RGB/YUV 원시 전송을 피하고 JPEG를 센서·카메라 쪽에서 유지해 Wi-Fi 전송량을 줄입니다.

```powershell
python tools/build_vision_cam.py --release                    # balanced 최신 합본
python tools/build_vision_cam.py --release --profile detail   # detail로 최신 합본 교체
```

두 명령은 **컴파일·합본 생성만** 합니다. `build/vision_cam/latest/`에는 가장 최근 성공한 프로필의
`mechdog_vision_cam_0x0.bin`, `.sha256`, `manifest.json`만 둡니다. manifest에서 버전·프로필·FQBN·크기·해시를 확인합니다.
새 컴파일·합본 검증이 실패하면 이전 성공 배포물을 교체하지 않습니다. 비밀 설정이 들어간 빌드는 배포물 생성을 거부합니다.
과거 펌웨어는 Git 이력으로만 복원하고 사용자가 만든 **실물 전체 플래시 백업은 삭제하지 않습니다.**

## Pi 처리 방식과 실물 합격 기준

영상 수신 스레드는 계속 최신 JPEG 한 장만 보관합니다. 모델은 처리할 때 최신 프레임을 가져오고,
느리면 중간 프레임을 건너뜁니다. 디코딩·추론 때문에 네트워크 수신을 멈추거나 모든 프레임을 큐에 쌓지 않습니다.
카메라의 실제 드라이버 취득 시각으로 나이를 계산하므로 보관 버퍼·전송 지연도 오래된 영상 판정에 포함됩니다.

첫 후보는 사람/자세에 맞는 경량 모델입니다. 예를 들어 공식 Pose Landmarker는 사람의 랜드마크를 추정하고
내부 입력은 256×256입니다. 이것이 낙상 분류를 직접 제공하거나 Pi에서 특정 FPS를 보장한다는 뜻은 아닙니다.
[공식 모델 설명](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker).
Ubuntu 24.04 ARM64·Python 3.12 설치 지원, 코드와 가중치 라이선스, 두 대의 실제 성능은 별도 확인해야 합니다.
Raspberry Pi 전용 AI Camera/NPU 벤치마크를 우리 ESP32-S3 카메라·CPU 추론 결과로 대신하지 않습니다.

사용자가 카메라 A 다음 B를 백업·굽기·확인한 뒤 두 대를 동시에 측정합니다.

1. `/status`: `camera.psram=true`, 실제 센서·width·height·quality·profile·target_fps 확인.
2. 10분 동시 수신: 실효 FPS·`camera.jpeg_kbps`·프레임 나이·RSSI·실패/재초기화 횟수·Pi CPU/온도 기록.
3. **초기 목표 [가정]**: 각 카메라 수신 10fps 이상, 수신 나이 p95 300ms 이하, 추론 선택 처리 5fps/대 이상,
   결과 나이 p95 500ms 이하. 목표 미달이면 프로필·모델·동시 작업을 조정하고 합격 처리하지 않습니다.
4. 실제 장면 크기는 `/status.camera.frame_bytes`로 측정합니다.
   예를 들어 50KB×15fps×2대는 JPEG 본문만 약 12Mbps입니다. 이 값은 용량 계산 예시이며 실측치가 아닙니다.
   점검용 브라우저 수신자를 추가하면 전송량도 추가됩니다.
5. 카메라가 앞쪽 낮은 위치에 있으므로 사람이 프레임 안에 충분히 들어오는지, 다리 흔들림·역광·거리별
   윤곽이 유지되는지 대체물로 확인합니다. 영상·얼굴을 저장소나 이슈에 올리지 않습니다.
6. 문제가 생기면 [카메라 복구 절차](vision-cam-firmware.md#5-복구)대로 사용자의 전체 플래시 백업 또는 기본 영상 펌웨어로 복구합니다.
