# 로봇 ↔ Pi 5 통신 규약 v0

로봇(MechDog 메인 ESP32, MicroPython)과 Raspberry Pi 5(고정 위치) 사이의 메시지 규약입니다.
로봇 쪽 구현은 Claude(`robot/`, `custom_sensors/`), Pi 5 쪽 구현은 Codex(`host/`, `tools/mock/`)가 이 문서를 기준으로 합니다.
규약을 바꿀 때는 이 문서를 먼저 고치고 PR로 상대 에이전트의 리뷰를 받습니다.

관련 문서: [MechDog 제어 API 규칙](dev/mechdog-api.md) 9절, [라이다 연동 설계](lidar-integration.md) 6절, [시연 시나리오](demo-scenario.md)

표기: **[가정]** 실측 전 초기값 — 실물에서 재고 이 문서를 고칩니다. **[확인 필요]** 실물에서 동작을 확인해야 하는 것.

## 1. 한눈에 보기

| 채널 | 방향 | 방식 | 포트 | 주기 |
| --- | --- | --- | --- | --- |
| 명령 | Pi 5 → 로봇 | UDP, 텍스트 한 줄 | 9100 | **10 Hz 고정**(변화 없어도 보냄) |
| 텔레메트리 | 로봇 → Pi 5 | UDP, 텍스트 한 줄 | 9101 | 10 Hz |
| 라이다 원시 데이터 | 로봇(서버) ↔ Pi 5(클라이언트) | TCP, 바이트 그대로 양방향 | 20108 | 연속 |

핵심 원칙

1. **판단은 Pi 5, 동작과 정지는 로봇.** 로봇은 받은 명령을 공식 API로 실행만 하고, 명령이 끊기면 스스로 멈춥니다.
2. **멈추는 쪽이 기본값.** 모르는 메시지, 범위 밖 값, 통신 끊김, 낮은 배터리는 모두 정지 쪽으로 처리합니다.
3. **Pi 5는 텔레메트리만 믿습니다.** "정지시켰다", "래치를 풀었다"는 Pi 5의 기억이 아니라 로봇이 보고한 값으로 판단합니다.

## 2. 공통 형식 (명령·텔레메트리)

메시지 모양은 제조사 시리얼 통신 강좌·군집 제어 예제가 쓰는 **"시작어 `|` 필드 … `|` `$`"** 형식에 맞춥니다.
제조사 예제에 익숙한 사람이 바로 읽을 수 있고, 같은 방식(시작어부터 `$`까지 잘라 `|`로 나누기)으로 파싱할 수 있습니다.

```text
명령:        CMD|<이름>|<robot_id>|<seq>|<인자...>|$
텔레메트리:  TEL|<robot_id>|<tseq>|...|<warn>|$
```

- 시작어는 명령 `CMD`, 텔레메트리 `TEL`. 마지막 필드는 항상 `$`(끝 표시)입니다.
- 명령의 둘째 필드가 명령 이름(`MOVE`, `STOP`, …, 대문자)입니다. 제조사 예제의 숫자 기능 코드 대신 이름을 써서
  로그만 보고도 뜻을 알 수 있게 합니다.
- UDP 데이터그램 하나에 메시지 **하나**. 인코딩 ASCII. `$` 뒤의 `\n`(또는 `\r\n`)은 있어도 없어도 됩니다.
- 받는 쪽은 데이터그램에서 **처음 나오는 시작어부터 그 뒤 처음 나오는 `$`까지** 잘라 `|`로 나눕니다.
  시작어 앞이나 `$` 뒤의 바이트는 무시합니다. 시작어나 `$`가 없으면 잘못된 메시지입니다.
- 필드 안에 `|`, `$`, 공백을 쓰지 않습니다(텔레메트리 `warn`만 쉼표로 여러 값).
- 명령 최대 길이 **64바이트**, 텔레메트리 최대 **160바이트**(`$`까지). 넘으면 잘못된 메시지로 봅니다.
- 정수는 10진수 ASCII(부호 `-` 허용, `+`·소수점·앞뒤 공백 불가). 실수는 소수점 아래 1자리까지(`-12.5`).
- 값을 모를 때(센서 읽기 실패)는 숫자 대신 `NA`를 씁니다. `0`으로 바꾸지 않습니다.

### 2.1 로봇 ID

| ID | 뜻 |
| --- | --- |
| `A`, `B` | 로봇 A, 로봇 B. 각 로봇의 `robot/config.py`에 고정 |
| `*` | 모든 로봇. **`STOP`·`ESTOP`에서만** 허용(대시보드 "전체 정지") |

- 자기 ID가 아닌 메시지는 조용히 버립니다(정지·래치 없음). 그 메시지가 다른 로봇용일 수 있기 때문입니다.
- `STOP`·`ESTOP` 외의 명령에 `*`를 쓰면 잘못된 명령(4.4절)입니다.

### 2.2 순번 `seq`와 `boot_id`

- `seq`: Pi 5가 붙이는 0 이상 정수(최대 2147483647), 로봇마다 따로 **1씩 단조 증가**. 같은 seq를 두 번 쓰지 않습니다.
- 로봇은 마지막으로 받아들인 seq(`last_cmd_seq`) **이하인 명령을 버립니다**(무선 지연으로 늦게 온 옛 명령 차단).
  버린 명령은 감시 타이머를 갱신하지 않습니다. 예외: `STOP`·`ESTOP`은 seq가 낮아도 실행합니다(멈추는 명령은 늦게 와도 해가 없음).
- `boot_id`: Pi 5 쪽 프로그램이 시작할 때마다 새로 만드는 값(영문·숫자 1~16자, 예: 시작 시각의 16진수나 난수).
  10 Hz로 2147483647까지는 약 6.8년이므로 seq가 넘치는 경우는 다루지 않습니다.

**Pi 5 재시작 절차 (`HELLO`)**

1. Pi 5 프로그램이 시작하면 새 `boot_id`를 만들고 `CMD|HELLO|<robot_id>|<boot_id>|0|$`을 보냅니다(`0`은 규약 버전).
   `HELLO`는 seq 자리에 `boot_id`가 들어가는 유일한 명령입니다.
2. 로봇은 `boot_id`가 지금 기억한 값과 **다르면**: `mechdog.move(0, 0)`으로 정지하고, `last_cmd_seq`를 **0**으로 되돌리고,
   새 `boot_id`를 기억합니다. **래치 상태는 그대로 둡니다**(재시작이 래치를 풀지 않음).
   같으면 아무것도 바꾸지 않습니다(재전송해도 안전).
3. 로봇은 다음 텔레메트리부터 새 `boot_id`를 보고합니다. Pi 5는 텔레메트리의 `boot_id`가 자기 값과 같아진 것을 본 뒤
   seq 1부터 명령을 보냅니다. 같아질 때까지 `HELLO`를 0.5초마다 다시 보냅니다.
4. 로봇은 `boot_id`를 모르는 상태(로봇 부팅 직후)에서는 `HELLO` 외의 명령을 받아도 `STOP`·`ESTOP`만 실행합니다.

규약 버전이 `0`이 아니면 로봇은 `HELLO`를 받아들이지 않고 텔레메트리 `warn`에 `proto`를 남깁니다.

## 3. 명령 (Pi 5 → 로봇, UDP 9100)

| 명령 | 형식 | 로봇 동작 (공식 API) |
| --- | --- | --- |
| 이동 | `CMD\|MOVE\|<id>\|<seq>\|<step_mm>\|<angle_deg>\|$` | `mechdog.move(step, angle)` |
| 정지 | `CMD\|STOP\|<id>\|<seq>\|$` | `mechdog.move(0, 0)` |
| 동작 그룹 | `CMD\|ACTION\|<id>\|<seq>\|<name>\|$` | `mechdog.action_run(name)` (3.3절 허용 목록만) |
| 자세 | `CMD\|POSE\|<id>\|<seq>\|<pose>\|$` | 3.4절 |
| 비상 정지 | `CMD\|ESTOP\|<id>\|<seq>\|$` | `mechdog.move(0, 0)` + 래치(`estop`) |
| 래치 해제 요청 | `CMD\|RESET\|<id>\|<seq>\|$` | 5.3절 조건을 만족하면 래치 해제 |
| 생존 확인 | `CMD\|PING\|<id>\|<seq>\|$` | 동작 없음. 감시 타이머만 갱신 |
| 재시작 알림 | `CMD\|HELLO\|<id>\|<boot_id>\|<proto>\|$` | 2.2절 |

예: `CMD|MOVE|A|3381|40|-10|$`, `CMD|ESTOP|*|902|$`, `CMD|ACTION|B|17|nodding_motion|$`

아래 본문에서는 짧게 쓰려고 `CMD|`·`|$`를 빼고 이름만(`MOVE`, `STOP` …) 적습니다.

### 3.1 보내는 규칙 (Pi 5)

- 로봇마다 **100 ms 간격으로 계속** 보냅니다. 보낼 것이 없으면 현재 의도를 다시 보냅니다:
  걷는 중이면 같은 `MOVE`, 서 있으면 `STOP`, 래치 중이면 `PING`.
- 걷기를 계속하려면 **`MOVE`를 계속 보내야 합니다.** `PING`만 오면 로봇은 걷기를 멈춥니다(5.1절의 이동 유효시간).
- 한 주기에 여러 명령이 필요하면 seq를 하나씩 올려 차례로 보냅니다.

### 3.2 `MOVE` 값 범위

| 필드 | 범위 | 단위·뜻 | 근거 |
| --- | --- | --- | --- |
| `step_mm` | -100 ~ 100 | 보폭 mm, 음수 = 후진 | mechdog-api.md 3절 |
| `angle_deg` | -30 ~ 30 | 회전, 양수 = 왼쪽 | mechdog-api.md 3절 |

- 범위 밖 정수는 로봇이 **경계값으로 잘라서** 실행하고 텔레메트리 `warn`에 `clipped`를 남깁니다.
- 정수가 아닌 값(`12.5`, `abc`, 빈 칸)은 잘못된 명령(4.4절)입니다.
- `CMD|MOVE|A|<seq>|0|0|$`은 `STOP`과 같은 효과입니다.

### 3.3 `ACTION` 허용 목록

현장 기능에는 mechdog-api.md 4.1절의 "기본·대기 / 정지·대기 / 확인 신호 / 사람 인식 시 신호" 용도만 허용합니다.

| 이름 | 용도 |
| --- | --- |
| `stand_four_legs` | 기본·대기 |
| `normal_attitude` | 기본·대기 |
| `sit_dowm` | 정지·대기 (문서 철자 그대로) |
| `go_prone` | 정지·대기 |
| `nodding_motion` | 확인 신호(도착 신호 등) |
| `scrape_a_bow` | 사람 인식 시 신호 |

- 이 목록에 없는 이름(시연용 `handshake`·`stretch_oneself`·`rotation_*`, 시연 전용 `stand_two_legs`·`boxing` 등, 오타)은
  **실행하지 않고** 잘못된 명령(4.4절)으로 처리합니다. 목록을 늘리려면 이 문서를 고치는 PR에 이유를 적습니다.
- 동작 그룹은 끝날 때까지 기다리지 않는 호출이므로, 로봇은 동작별 소요 시간(`robot/config.py`, 초기값 2~4초 **[가정]**) 동안
  `state=action`으로 두고 그동안 온 `MOVE`·`ACTION`·`POSE`는 실행하지 않습니다(`warn=busy`). `STOP`·`ESTOP`은 실행합니다.
- 동작이 끝난 뒤 첫 `MOVE` 전에 로봇이 `mechdog.set_default_pose()`를 먼저 부르고 자세가 잡힐 때까지(초기값 600 ms **[가정]**) 기다립니다.
- 소요 시간은 **최대값**입니다. 동작 시작 뒤 `ACTION_MIN_MS`(초기값 200 ms **[가정]**)가 지나면 `mechdog.action_is_over()`도 확인해
  끝났다고 나오면 일찍 `action`을 끝냅니다(제조사 예제). 읽기에 실패하면 끝나지 않은 것으로 봅니다.
- 최대 시간이 지나도 끝났다고 확인되지 않으면 로봇이 `mechdog.stop_action()`과 `mechdog.move(0, 0)`을 부르고 `action`을 끝내되,
  그 동작 그룹은 **끝났다고 확인될 때까지 계속 추적**합니다(그 사이 래치가 걸리면 다시 멈춤을 시도).
- 동작 그룹이 끝났다고 확인되기 전에 래치(`ESTOP`·통신 끊김·저전압·잘못된 명령)가 걸리면 `mechdog.stop_action()`으로 동작 그룹을 멈추고
  `mechdog.move(0, 0)`도 함께 부릅니다. `stop_action()`이 실제로 바로 멈추는지는 **[확인 필요]** 이므로, 이때 래치 해제(`RESET`)는
  `action_is_over()`의 보고와 상관없이 **그 동작의 최대 시간이 지난 뒤에만** 됩니다. 단순 `STOP`은 동작 그룹을 끊지 않고 `move(0, 0)`만 부릅니다.

### 3.4 `POSE`

동작 종료가 확인되지 않으면 최대 시간이 지난 뒤에도 `busy`를 유지합니다. 새 이동·자세·동작과 RESET을
허용하지 않으며, 종료 확인 호출은 참 또는 정수 1만 완료로 받아들입니다.

| `pose` | 로봇 동작 |
| --- | --- |
| `default` | `mechdog.set_default_pose()` |
| `sit` | `mechdog.action_run("sit_dowm")` |
| `prone` | `mechdog.action_run("go_prone")` |

- `sit`·`prone`은 동작 그룹이므로 3.3절의 소요 시간·`busy` 규칙을 그대로 따릅니다.
- 다른 값은 잘못된 명령(4.4절)입니다.

## 4. 로봇이 명령을 처리하는 순서

```text
수신 → 길이·인코딩 확인 → CMD~$ 잘라내기 → | 로 나누기 → 로봇 ID 확인(남의 것이면 버림)
     → ESTOP/STOP 이면 seq와 상관없이 즉시 실행
     → HELLO 면 2.2절
     → seq <= last_cmd_seq 이면 버림
     → last_cmd_seq 갱신, 감시 타이머 갱신
     → 래치 중이면 RESET·PING 외에는 실행하지 않음(warn=latched)
     → 명령 실행
```

### 4.1 우선순위

`ESTOP` > `STOP` > `RESET` > `MOVE`·`ACTION`·`POSE` > `PING`

- `ESTOP`은 상태(동작 중, 래치 중, `boot_id` 모름)와 seq에 상관없이 **항상** 실행합니다.
- 한 데이터그램에는 명령 하나만 있으므로 "동시에 온" 명령은 없습니다. 우선순위는 위 처리 순서와 래치 규칙으로 지켜집니다.

### 4.2 래치 중에 받는 명령

| 명령 | 래치 중 처리 |
| --- | --- |
| `ESTOP` | 실행(래치 사유를 `estop`으로 바꿈) |
| `STOP` | 실행(이미 정지 상태) |
| `RESET` | 5.3절 |
| `PING`, `HELLO` | 처리 |
| `MOVE`, `ACTION`, `POSE` | **실행하지 않음**, `warn=latched` |

### 4.3 텔레메트리 `last_cmd_seq`

로봇이 **받아들인**(버리지 않은) 마지막 명령의 seq입니다. Pi 5는 이 값으로 명령이 도착했는지 확인합니다.
seq와 상관없이 실행한 늦은 `STOP`·`ESTOP`은 `last_cmd_seq`를 낮추지 않습니다.

### 4.4 잘못된 명령

다음은 **자기 ID(또는 `*`)가 붙은** 메시지가 아래에 해당할 때입니다.

- 알 수 없는 메시지 종류, 필드 개수 틀림, 정수 아닌 값, 길이 초과, ASCII 아님
- `ACTION` 허용 목록 밖 이름, `POSE` 목록 밖 값, `STOP`·`ESTOP` 외 명령에 `*`

처리: `mechdog.move(0, 0)` → `latched=1`, `latch_reason=bad_cmd`. 래치를 풀려면 `RESET`이 필요합니다.
로봇 ID 필드까지도 읽을 수 없는 메시지(빈 데이터그램, `CMD`나 `$` 없음, 필드 3개 미만)는 누구 것인지 모르므로
버리고 `warn=garbage`만 남깁니다.

> 잘못된 명령에 래치까지 거는 이유: Pi 5 쪽 버그로 엉뚱한 값이 계속 오면 사람이 상황을 보고 풀게 하려는 것입니다.
> 시연 중 불편이 크면 "정지만 하고 래치는 안 함"으로 바꿀 수 있습니다(리뷰 의견 환영).

## 5. 안전 규칙

### 5.1 감시 타이머 (로봇)

| 이름 | 값 | 조건 | 로봇 동작 |
| --- | --- | --- | --- |
| 통신 끊김 `LINK_TIMEOUT_MS` | **600 ms** [가정] | 받아들인 명령(종류 무관)이 600 ms 동안 없음 | `move(0, 0)` + 래치 `link_lost` |
| 이동 유효시간 `MOVE_HOLD_MS` | **600 ms** [가정] | 걷는 중인데 받아들인 `MOVE`가 600 ms 동안 없음(`PING`만 옴) | `move(0, 0)`, 래치 없음, `warn=move_stale` |
| Wi-Fi 끊김 | 즉시 | `wlan.isconnected()`가 거짓 | `move(0, 0)` + 래치 `link_lost`, 재접속 시도 |

- 600 ms는 10 Hz 명령 6개분입니다. 너무 짧으면 무선 지연 때문에 걷다 서다를 반복하므로, 실측 왕복 지연을 보고 조정합니다.
  mechdog-api.md 9절의 "예: 0.5초"보다 조금 길게 잡은 이유가 이것입니다.
- 감시는 명령 수신과 **다른 스레드**(`Hiwonder.startMain`)에서 50 ms 이하 주기로 돌아, 수신 스레드가 멈춰도 정지합니다.
- 로봇은 부팅 직후 `latched=1`, `latch_reason=boot`로 시작합니다. 사람이 상태를 본 뒤 `RESET`해야 움직입니다.

### 5.2 래치

래치는 "사람이 확인하기 전까지 움직이지 않는" 상태입니다.

| `latch_reason` | 언제 |
| --- | --- |
| `none` | 래치 아님 |
| `boot` | 로봇 부팅 직후 |
| `link_lost` | 통신 끊김, Wi-Fi 끊김 |
| `estop` | `ESTOP` 받음 |
| `low_battery` | 저전압(5.4절) |
| `bad_cmd` | 잘못된 명령(4.4절) |

- 래치가 걸리는 순간 로봇은 `mechdog.move(0, 0)`을 부르고 `state=stopped`가 됩니다.
- 이미 래치 중에 다른 사유가 생기면 사유를 새 것으로 바꿉니다. 단 `estop`은 `RESET` 전까지 다른 사유로 덮어쓰지 않습니다.

### 5.3 래치 해제 (`RESET`)

- Pi 5는 **사람이 대시보드에서 해제 버튼을 누를 때만** `RESET`을 보냅니다. 자동으로 보내지 않습니다.
- 로봇은 아래를 모두 만족할 때만 래치를 풉니다. 하나라도 아니면 래치를 유지하고 `warn=reset_denied`를 남깁니다.
  1. Wi-Fi 연결됨
  2. 배터리를 읽을 수 있고 `LOW_BATT_RESET_MV` 이상(5.4절)
  3. 동작 그룹 실행 중이 아님
- 해제되면 `latched=0`, `latch_reason=none`, `state=idle`. **해제 자체로는 움직이지 않습니다.** 다음 `MOVE`(RESET보다 큰 seq)부터 움직입니다.
- Pi 5는 텔레메트리에서 `latched=0`을 본 뒤에야 해제된 것으로 표시합니다. 1초 안에 안 바뀌면 대시보드에 "해제 실패"와 `warn`을 보여 줍니다.

### 5.4 저전압

배터리는 7.4 V 2셀 리튬 배터리(완충 8.4 V), 보드 입력 범위 6~8.4 V입니다([라이다 연동 설계](lidar-integration.md) 5절).
값은 `Hiwonder.Battery_power()`(제조사 예제 기준 mV)로 읽습니다.

| 이름 | 값 | 동작 |
| --- | --- | --- |
| `LOW_BATT_WARN_MV` | **7000 mV** (셀당 3.5 V) [가정] | `warn=batt_low`. 대시보드에 충전 권고 |
| `LOW_BATT_LATCH_MV` | **6600 mV** (셀당 3.3 V) [가정] | **2초 연속** 이 값 미만이면 `move(0, 0)` + 래치 `low_battery` |
| `LOW_BATT_RESET_MV` | **6800 mV** [가정] | 이 값 이상이어야 `RESET`으로 해제(오르내림 반복 방지) |
| 읽기 실패 | — | `battery_mv=NA`, `warn=batt_unknown`. **3초 연속** 실패하면 래치 `low_battery` |

- 걷는 동안 서보 전류로 전압이 순간적으로 내려가므로 "연속 2초" 조건을 둡니다. 실측 후 조정합니다.
- 모르는 배터리 값을 "충분함"으로 보지 않습니다.

### 5.5 전체 정지 (대시보드)

대시보드의 전체 정지는 `CMD|ESTOP|*|<seq>|$`를 **각 로봇 주소로** 보냅니다(브로드캐스트 주소 하나에만 의존하지 않음).
각 로봇의 seq는 따로 관리하므로 로봇별로 자기 seq를 씁니다. 로봇은 seq와 상관없이 실행합니다(4.1절).

## 6. 텔레메트리 (로봇 → Pi 5, UDP 9101)

```text
TEL|<robot_id>|<tseq>|<last_cmd_seq>|<state>|<latched>|<latch_reason>|<battery_mv>|<tilt_x>|<tilt_y>|<uptime_ms>|<boot_id>|<warn>|$
```

| 필드 | 형식 | 뜻 |
| --- | --- | --- |
| `robot_id` | `A`/`B` | 보낸 로봇 |
| `tseq` | 정수 | 텔레메트리 순번. 로봇 부팅 때 0부터 1씩 증가 |
| `last_cmd_seq` | 정수 | 4.3절. 아직 없으면 `0` |
| `state` | `idle`/`moving`/`action`/`stopped` | 서 있음 / 걷는 중 / 동작 그룹 중 / 래치로 정지 |
| `latched` | `0`/`1` | 래치 여부 |
| `latch_reason` | 5.2절 | |
| `battery_mv` | 정수 또는 `NA` | `Hiwonder.Battery_power()` 값 |
| `tilt_x`, `tilt_y` | 실수(도) 또는 `NA` | `Hiwonder_IIC.MPU(...).read_angle()`의 0번·1번 값 |
| `uptime_ms` | 정수 | 로봇 부팅 후 시간(`time.ticks_ms()` 기준, 넘침은 로봇이 보정) |
| `boot_id` | 문자열 또는 `-` | 로봇이 기억한 Pi 5 `boot_id`. 모르면 `-` |
| `warn` | `none` 또는 쉼표로 이은 낱말 | 6.1절 |

- `tilt_x`·`tilt_y`가 롤·피치 중 어느 것인지는 제조사 자료 안에서 설명이 엇갈립니다(mechdog-api.md 4.2절).
  실물에서 확인하기 전에는 이름을 `roll`/`pitch`로 붙이지 않습니다 **[확인 필요]**.
- 보내는 곳: `robot/config.py`의 `PI_HOST`가 정해져 있으면 그 주소, 없으면 **마지막으로 받아들인 `HELLO`를 보낸 주소**의 9101 포트.
  둘 다 없으면 보내지 않습니다.
- 래치 상태가 바뀌거나 `ESTOP`을 받으면 10 Hz 주기를 기다리지 않고 **즉시 한 번 더** 보냅니다.
- 필드는 앞으로 **`$` 바로 앞에만** 추가합니다. Pi 5는 아는 필드 뒤의 남는 필드를 무시합니다.

예:

```text
TEL|A|5120|3381|moving|0|none|7650|1.2|-0.4|512034|6f3a91|none|$
TEL|B|88|0|stopped|1|boot|NA|NA|NA|8810|-|batt_unknown|$
TEL|A|5131|3390|stopped|1|link_lost|7610|0.8|-0.2|513141|6f3a91|none|$
```

### 6.1 `warn` 낱말

`warn`은 **지난 텔레메트리 이후** 생긴 일과 지금 계속되는 상태를 함께 담습니다. 여러 개면 쉼표로 잇습니다(`clipped,batt_low`).

| 낱말 | 뜻 |
| --- | --- |
| `clipped` | `MOVE` 값을 범위로 잘라냄 |
| `busy` | 동작 그룹 중이라 명령을 실행하지 않음 |
| `latched` | 래치 중이라 명령을 실행하지 않음 |
| `move_stale` | `MOVE`가 끊겨 걷기를 멈춤(5.1절) |
| `reset_denied` | `RESET` 조건 불충족 |
| `garbage` | 누구 것인지 모를 메시지를 버림 |
| `proto` | 지원하지 않는 규약 버전의 `HELLO` |
| `batt_low` | `LOW_BATT_WARN_MV` 미만 |
| `batt_unknown` | 배터리 읽기 실패 |
| `imu_unknown` | 기울기 읽기 실패 |
| `pm_on` | Wi-Fi 절전 끄기(`PM_NONE`)가 지원되지 않아 절전이 켜져 있음 — 지연이 클 수 있음 |
| `lidar_uart` | 라이다 UART를 열지 못함(7절) |

### 6.2 Pi 5가 텔레메트리를 다루는 규칙

- 텔레메트리가 **1초 동안** 안 오면 그 로봇을 "연결 끊김"으로 표시합니다. 로봇은 이미 스스로 멈췄다고 가정하지 말고,
  대시보드에 "상태 모름"으로 보여 줍니다.
- 정지·래치·해제 여부는 텔레메트리의 `state`·`latched`로만 판단합니다.
- `tseq`가 줄어들면(로봇 재부팅) `uptime_ms`도 함께 확인하고, 로봇이 `boot` 래치 상태임을 보여 줍니다.

## 7. 라이다 원시 중계 (TCP 20108)

[라이다 연동 설계](lidar-integration.md) 6.2절 **A안**: 로봇은 라이다 UART 바이트를 **해석하지 않고** 그대로 넘깁니다.

| 항목 | 규칙 |
| --- | --- |
| 역할 | 로봇이 TCP 서버, Pi 5가 클라이언트(sllidar_ros2 TCP 채널 또는 socat 가상 시리얼) |
| 방향 | 라이다 TX → 로봇 UART RX → TCP → Pi 5 / Pi 5 → TCP → 로봇 UART TX → 라이다 RX |
| 가공 | **없음.** 프레이밍·헤더·압축·변환 없이 받은 바이트를 같은 순서로 보냄 |
| UART | 115200 bps, 8N1, J5: IO32 = 로봇 RX, IO33 = 로봇 TX(방향 **[확인 필요]**) |
| 클라이언트 수 | **한 번에 하나.** 새 연결이 오면 기존 연결을 닫고 새 연결로 바꿈(Pi 5 드라이버 재시작 시 반쯤 끊긴 옛 연결이 자리를 막지 않게) |
| 클라이언트 없을 때 | UART로 들어온 바이트는 읽어서 버림(연결 직후 오래된 데이터가 한꺼번에 가지 않게) |
| 연결 끊김 | 로봇은 소켓을 닫고 다음 연결을 기다림. 라이다에 따로 명령을 보내지 않음(모터는 CTRL_MOTO 상시 ON) |

- 라이다 중계는 **로봇을 움직이지 않으며, 안전 래치와 무관**합니다. 라이다가 끊겨도 로봇은 정지하지 않습니다.
  라이다가 없을 때 멈출지는 Pi 5가 판단해 `STOP`을 보냅니다.
- 로봇은 바이트를 일부러 버리지 않습니다. 다만 TCP 전송이 밀리면 UART 수신 버퍼(초기값 4096바이트 **[가정]**)가 넘쳐
  바이트를 잃을 수 있습니다. 이때 Pi 5 쪽 드라이버가 스캔 패킷 경계를 다시 찾아야 합니다.
- **라이다에는 `machine.UART`를 씁니다**(mechdog-api.md 6절 예외). 제조사 자료에서 공식 `Hiwonder.UART`는 통신 속도만 인자로 받고,
  메서드도 `CMD~$` 텍스트 명령용(데이터 포함 여부 확인, 명령 한 줄 읽기·나누기, 문자열 보내기)만 있습니다.
  라이다의 바이너리 바이트(`0xA5 …`)를 그대로 읽고 쓰는 방법이 없어 원시 중계에 쓸 수 없습니다.
- UART 번호·`rxbuf` 키워드가 펌웨어에서 지원되는지는 **[확인 필요]** 입니다. UART를 열지 못하면 TCP 서버는 열되
  연결을 받자마자 닫고, 텔레메트리 `warn`에 `lidar_uart`를 남깁니다. 명령·텔레메트리는 그대로 동작합니다.

## 9. 예시 흐름

**정상 시작**

```text
로봇 부팅                     TEL|A|0|0|stopped|1|boot|7900|0.3|0.1|1200|-|none|$
Pi 5 → CMD|HELLO|A|6f3a91|0|$
                              TEL|A|4|0|stopped|1|boot|7900|0.3|0.1|1600|6f3a91|none|$
(사람이 대시보드에서 해제)
Pi 5 → CMD|RESET|A|1|$
                              TEL|A|6|1|idle|0|none|7900|0.3|0.1|1800|6f3a91|none|$
Pi 5 → CMD|MOVE|A|2|40|0|$   (100 ms마다 seq 3, 4, ...)
                              TEL|A|7|2|moving|0|none|7820|0.9|-0.6|1900|6f3a91|none|$
```

**통신 끊김**

```text
Pi 5 → CMD|MOVE|A|57|40|0|$   (이후 Wi-Fi 지연으로 600 ms 동안 아무것도 안 옴)
로봇: move(0, 0), 래치        TEL|A|..|57|stopped|1|link_lost|...|$
Pi 5 → CMD|MOVE|A|58|40|0|$   (늦게 도착) → 래치 중이라 실행 안 함, warn=latched
사람이 확인 후 RESET → 해제 → 새 MOVE부터 다시 이동
```

**늦게 온 옛 명령**

```text
Pi 5 → CMD|MOVE|A|10|60|0|$, CMD|MOVE|A|11|0|0|$ 를 차례로 보냄
로봇에 11이 먼저, 10이 나중에 도착 → 10은 seq <= 11 이므로 버림 (로봇은 서 있음)
```

## 10. v0의 한계와 열린 질문

- **인증이 없습니다.** 같은 Wi-Fi에 있는 누구나 `MOVE`를 보낼 수 있습니다. v0은 **시연 전용 공유기(WPA2, 외부 인터넷 분리)** 를
  전제로 합니다. 이후 버전에서 공유 비밀값 기반 메시지 확인(예: HMAC 앞부분)을 검토합니다.
- 600 ms 타임아웃, 저전압 임계, 동작 소요 시간은 모두 실측 전 값입니다.
- `mechdog.stop_action()`·`mechdog.move(0, 0)`이 실행 중인 동작 그룹을 바로 끊는지 **[확인 필요]**(3.3절).
- 넘어짐(기울기 큼) 감지 래치는 v0에 넣지 않았습니다. 실물에서 `read_angle()` 값을 본 뒤 추가를 검토합니다.
- 비전 모듈 영상은 이 규약 밖입니다(비전 모듈 기본 펌웨어의 HTTP 스트림을 Pi 5가 직접 받음, **[확인 필요]**).
- [라이다 연동 설계](lidar-integration.md) 6.3절의 메시지 초안(`CMD|<seq>|<step>|<angle>|$`, `STAT|...`)과 7절 예시 코드의
  500 ms 타임아웃은 이 문서로 대체됩니다.
- 로봇 코드는 제조사 예제처럼 "전역 초기화 → 루프 함수들 → `Hiwonder.startMain` 등록" 구조로 씁니다. Python Editor는 여러 파일을
  장치에 내려받을 수 있으나(장치 파일 목록에 각각 표시), `main.py`에서 다른 파일을 `import`해 쓰는 것은 **[확인 필요]** 입니다.
  안 되면 `main.py` 한 파일로 합쳐 올릴 수 있게 만듭니다.
